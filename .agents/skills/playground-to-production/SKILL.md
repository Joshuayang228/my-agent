# Playground → 正式 UI 回流

用于把 Playground 中已经被用户明确确认的候选方案，选择性同步到正式产品页面。这个 Skill 不负责设计新方案，也不把 Playground 原样复制到生产。

## 适用时机

仅在以下条件满足后进入 P1 回流：

- P0 候选已经在 Playground 中完成默认态和关键边缘态验收；
- 用户明确说“回流”“改正式页面”或等价的授权语句；
- 已能指出正式产品的目标页面、真实数据来源和受影响的测试；
- 当前工作区状态已检查，且不会覆盖其他 Agent 的未提交修改。

如果只有“方向合理”“继续研究”或“先做做看”，停留在 P0 研究 / 候选阶段。

## 回流状态

按以下状态推进，不得跳级：

```text
candidate
  → playground-validated
  → user-approved
  → production-ready
  → adopted
```

- `candidate`：想法、参考或尚未完成的候选。
- `playground-validated`：Playground 已覆盖关键视觉、交互和边缘状态。
- `user-approved`：用户明确批准了具体候选和回流范围。
- `production-ready`：正式落点、真实数据路径、错误处理、权限边界和测试方案已明确。
- `adopted`：已进入正式调用链，验证和文档收口完成。

用户确认只能推进到 `user-approved`，不能直接把资产标记为 `adopted`。

## 核心边界

- **Playground 是候选**：允许 fixture、来源路径、采用标记、调试滑杆、组件目录、隔离占位和实验 Tab；默认不得读写真实会话、设置、LLM 或生产数据。
- **正式 UI 是产品**：只接收已确认、可解释、能服务真实产品流程的视觉规则和交互能力；不显示 `.tsx` 来源、注册表 key、实验控制器或“隔离样张”文案。
- **基础与体验分层不变**：通用按钮、输入、卡片、徽标、标签、分隔线等基础能力只能从 Foundation 进入 Experience；业务结构不能为了复用而伪装成基础组件。
- **候选状态不等于采用**：故事可见、测试通过或参考项目已有实现，都不能自动把资产状态改成 `adopted`。只有真实生产调用链和对应证据成立时才可更新生命周期。

## 回流输入与证据

开始施工前，先建立一张候选映射表。每个候选项至少记录：

| 字段 | 要回答的问题 |
|------|--------------|
| 候选身份 | 哪个合同、哪个 Playground story、哪个稳定 key？ |
| 用户结论 | 确认了什么，否决了什么，哪些仍待确认？ |
| 生产落点 | 正式页面、组件、入口或数据流程在哪里？ |
| 数据路径 | 真实状态来自哪个组件、IPC、服务或存储？ |
| 迁移类型 | 直接回流、生产改造后回流，还是留在 Playground？ |
| 保留内容 | 哪些来源信息、fixture、调试控件必须留在 Playground？ |
| 验收证据 | 哪些 Unit、E2E、截图或手工检查证明它可用？ |

没有生产落点或真实数据路径的候选，不能直接进入正式实现；先判断是否需要新的施工合同。

每次回流开始时，先在回复或工作记录中生成以下回流记录；无法填写的字段标记为“未满足”，不得用推测补齐：

```text
回流对象：
来源合同 / Story / 稳定 key：
用户授权原话与范围：
批准内容：
明确排除：
生产落点：
真实数据路径：
跨层影响：
迁移分类：
保留在 Playground 的内容：
测试证据：
文档变更：
资产生命周期：
未解决风险：
最终结论：
```

## 固定流程

### 1. 先做回流审计

读取当前施工合同、前端规范、架构和受影响模块卡，检查工作区状态，并逐项回答：

- 用户是否明确许可回流，而不是只说“方向合理”或“继续研究”？
- 这项东西是正式产品能力，还是只为开发者看实现的展厅信息？
- 正式页面是否已有真实调用点、数据契约和关闭/错误/窄宽行为？
- 是否会改变默认布局、数据、IPC、持久化、权限或模型行为？
- 正式“文件/预览”这类拆分 Tab 是否共享必要状态，避免切换后丢失上下文？

范围不清时先停在审计，不用代码猜测用户意图。

审计顺序固定为：`施工合同 → 工作区状态 → 正式调用方 → 数据 / IPC → 当前渲染 → 测试证据 → Alice / 其他参考`。参考项目只能帮助解释交互方向，不能替代本项目的真实契约。

审计结果必须逐项标记为 `通过`、`不通过` 或 `不适用`。以下四道硬门禁全部通过后，才可进入正式实施：

1. **授权门禁**：用户明确批准具体候选和范围；被否决或未确认的部分已排除。
2. **隔离门禁**：已检查 `git status`，确认本次修改文件不与其他 Agent 的未提交修改重叠，且不会混入对方提交。
3. **契约门禁**：已找到正式入口、正式调用方、真实数据源，以及涉及的 IPC / 存储 / 权限 / Runtime 边界。
4. **证据门禁**：已有 Playground 验收证据，并已列出正式实现所需的 Unit、E2E、构建和文档验证。

### 2. 划分三类内容

对每个候选项标记：

1. **直接回流**：正式产品已有对应能力，只需统一 token、样式、布局或无障碍行为。
2. **生产改造后回流**：候选验证了方向，但正式实现还缺状态共享、真实数据契约、错误处理或测试，先补完整再回流。
3. **留在 Playground**：来源路径、组件目录、采用标记、调试滑杆、隔离数据、未落地候选和仅用于观察的展示控制。

禁止以“同步 Playground”为理由把第三类内容带入正式产品。

判定规则：

- 只有 token、通用组件状态、无障碍行为或已有真实流程的布局差异，才可能是“直接回流”；
- 只要涉及新状态、新数据契约、IPC、持久化、权限、共享选中状态或错误恢复，就先归“生产改造后回流”；
- 只服务开发者观察、实验控制、来源追踪、候选展示或静态夹具的内容，归“留在 Playground”。

只要授权、隔离、契约或证据任一门禁不通过，最终结论只能是“停留在 Playground”或“等待生产改造”，不得开始修改正式实现。

### 3. 先研究再改

优先查项目内真实实现和参考资料：

1. `src/components/`、`src/App.tsx`、`src/shared/` 及其测试；
2. 项目施工合同、模块卡、`docs/architecture.md`、`docs/quality.md`；
3. `_reference/framework-harness/` 中对应 Alice / Claude Code 参考；
4. 仅在现有方案不适用时才考虑新抽象或新依赖。

开始修改前，用一句话记录查了什么、为什么不能直接复用现有实现。

若正式页面已有实现，优先在正式组件上增加兼容 props 或调整结构；若候选中的业务结构只存在于 Playground，先把它拆成真实产品状态和数据契约，不复制 fixture 结构。

如果涉及新增或修改 IPC、存储、Prompt、权限、模型配置、Runtime、跨模块类型或正式默认行为，停止普通 UI 回流，先创建或补充施工合同，并重新进行审计。

### 4. 实施与测试

- 优先修改正式共享组件或 token；不要复制一套 Playground 皮肤。
- 新增 props 时保持生产默认兼容；Playground 专属差异必须显式传入。
- 真实数据路径保留真实 IPC/服务；只读 fixture 只能存在于 Playground 和测试。
- 颜色使用语义 token；圆角、动效、焦点、禁用、错误、键盘和窄宽状态一起考虑。
- 拆分 Tab 时补共享状态或明确的状态来源；测试至少覆盖切换前后上下文不丢失。
- 不引入 Storybook、Radix 等与当前合同无关的新依赖。

实施前先写清本次允许修改的文件清单；发现超出清单的文件时暂停并重新评估范围。生产测试必须验证正式入口和真实数据路径，不能只复用 Playground fixture 测试。

### 5. 文档与回流许可

正式回流后同步：

- 对应施工合同的生命周期、范围和验收标准；
- 受影响模块卡的“已落地能力”；
- `docs/architecture.md`（边界/数据流改变时）；
- `docs/quality.md`（测试门禁改变时）；
- `docs/progress.md` 和 `docs/changelog.md`；
- `agent-skills/frontend-guidelines.md`（形成可复用前端规则时）。

如果仍属于候选，就明确写为 Playground P0，不要把测试样张写成正式生产契约。

回流完成后，施工合同应明确哪些候选已进入 P1、哪些被否决或保留在 P0；若合同仍指导后续回流，不要提前冻结。资产状态更新必须绑定真实 source path、生产调用点和测试证据，不能只因为故事被用户确认就标记为 `adopted`。

### 6. 完成门禁

按项目顺序执行：

1. 自审：沿“定义 → 调用方 → 数据/IPC → 实际渲染 → 测试”检查；确认没有把展厅信息带入正式 UI。
2. `npm run test`
3. `npx tsc --noEmit`
4. 改了 UI/交互时运行 `npm run test:e2e`
5. 涉及 import、构建或打包时运行 `npm run build`
6. 涉及资产或文档时运行 `npm run assets:check`、`npm run docs:validate`
7. `git diff --cached --check` 后，再按仓库规则 commit + push。

测试失败、范围越界或生产行为与候选不一致时，停止声明完成，记录剩余问题并回到审计阶段。

以下任一情况必须停止回流：

- 用户授权范围不清，或候选包含尚未确认 / 已否决内容；
- 正式落点、真实数据路径或状态契约不存在；
- 需要 IPC、存储、权限、Prompt 或 Runtime 改动但没有施工合同；
- 工作区存在无法区分归属的未提交修改；
- 只能通过复制 Playground 页面、fixture 或实验控制器才能实现；
- 生产测试没有覆盖关键状态，或验证结果与候选不一致。

只有在正式调用链、测试和文档均收口后，才能把状态推进到 `adopted`。否则保留为 `user-approved` 或 `production-ready`，并明确剩余阻塞项。
