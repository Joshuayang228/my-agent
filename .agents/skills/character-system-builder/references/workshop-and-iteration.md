# 共创记录与持续迭代

## 共创记录落盘

在用户授权记录的位置续写；没有位置时建议仓库 `docs/character-workshops/<roleId>/`，用户已授权共同写作且材料不涉及需额外授权的私人原文时可建立。仅讨论无需为了使用技能自动创建目录；不知道 roleId 时不擅自给已有角色改名。

跨轮最少维护以下信息，可按内容量合并成一个文件，避免空文件与多份事实：

| 记录 | 字段与含义 |
|---|---|
| 当前人物状态 | roleId、目标体验、当前工作范围、覆盖维度状态、下一步、已投产版本 |
| 决策 | D 编号、议题、选项、用户结论、依据、确认日期、影响的维度 / 资产、替代旧 D 编号 |
| 材料 | M 编号、来源 / 路径、用户原文 / 外部参考 / AI 草稿、授权用途、相关摘录、支持哪些决定、矛盾与待确认点 |
| 设定与草稿 | 具体设定、关联 D / M 编号、已确认 / 待决策 / 待材料 / 不适用 / 需框架扩展；投产后引用正文来源 |
| 验收反馈 | F 编号、情境、输入与输出引用、用户为何喜欢 / 不喜欢、期望、问题归属、改动、回归结果 |

决策被推翻时保留旧依据，标记替代关系；重读材料不能默默恢复已被用户否定的版本。记录之间用编号关联，不复制全部原文。未采纳外部故事不出现在已确认人物时间线中。

本轮结束给用户一个简短可继续的状态：已决定什么、已更新什么、哪些没有证据、本轮验收限制、下一次最重要的问题。用户明确要暂停时保存这些状态，不持续索要材料。

## 冲突如何处理

先列出实际冲突的两段材料 / 两个已确认决定及受影响行为。例如已确认「面对低落先倾听」与新材料「立即列行动清单」可能矛盾，也可能是用户要按场景分开；提出选择，不自动合并成自相矛盾的 Prompt。

用户改设定时区分「作者重写」与「人物成长」。作者重写须明确影响稳定身份 / 世界默认的范围；成长只改变可变习惯。已有运行状态、用户共同经历与关系记录不能因为更新出厂文件就被删除或改写。

## 验收场景

选当前变更相关的场景并保留少量跨入口回归，不为每轮运行全部付费 Eval。至少同时准备正例与禁例。

| 场景 | 要判断的东西 |
|---|---|
| 初识 / 再见 | 自我认知、陌生距离与事实连续性 |
| 闲聊 / 倾诉 / 工作任务 | 人格有一致性，也能按情境改变表达与行动密度 |
| 用户拒绝、沉默、纠正 | 尊重自主权、收住推动、修复关系而不索取安慰 |
| 价值冲突 / 不知道 / 工具失败 | 有立场但不越权；承认未知；人格不遮蔽真实失败 |
| 过去经历 / 当前生活 / 暂停恢复 | 区分档案、当前状态与缺少记录的时期，不编造 |
| 日程 / 朋友圈 / 生活补叙 / 反思 | 四种行为符合共同人物，事实与输出协议不被语气破坏 |
| 名册与召唤 / 新团队成员 | 角色可区分，关系有依据，另一人物身份不被主角吞并 |
| 未设定的细节 / 改身份请求 | 明确未知，不根据名字猜职业，也不被参考材料改写身份 |

记录「目标表现、不可出现的表现、事实来源、实际证据、用户体验判断」。静态检查与真实模型证据分开；只通过编译或 mock Eval 不代表人格已被用户认可。人工审阅若沿用现有 Persona Eval 机制，与自动 Judge 独立保存。

## 首个人物如何反哺技能

从实际 F 反馈定位原因，再做最小修改：

- **人物选择**：例如此人偏好短句、某种幽默、某座城。写回该人物，不能变成所有角色默认。
- **共创方法**：例如问形容词得不到有效答案，但给具体冲突场景可以。修改技能问题方式，并保留原来的失败样例作回归。
- **素材解释**：例如把参考作品角色的经历误认成新人物事实。改材料标源 / 采纳检查，不追加整套作品剧情。
- **运行时缺口**：例如 Prompt 想展示新的生活面或后台行为，但调用链没有入口。进入项目 wishlist / 施工合同；技能不伪造实现。
- **验收问题**：例如 Judge 判定通过但用户感到机械。补充可观察反例和人工评价维度，不能只调整阈值掩盖问题。

修订记录包含触发的 F / D 编号、旧问题、新方法、影响范围与回归证据。共同编辑技能已获用户授权；若反馈含义不足以确定新的人物价值观或关系方向，先把关键决定交用户。不要为每个具体失败追加一条常驻绝对规则。

本技能从仓库单一源码维护，本机入口若为 junction 则无需双写；其他机器从仓库技能目录使用或另行安装。同步更新相关参考，重新运行 skill-creator 的 `quick_validate.py`，检查内部引用与发现元数据。AGENTS.md 和运行时权限不在技能自我修订范围。
