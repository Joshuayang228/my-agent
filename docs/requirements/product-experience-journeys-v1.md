# Chat 主旅程 v1 施工合同

> 状态：进行中
> 生命周期：E0 / E1 Playground 候选施工；用户已确认产品体验总体路线，正式 UI 仍需候选验收后再回流。
> 统一称呼：施工合同

## 1. 需求背景（Why）

基础组件阶段已经完成大部分视觉与交互基线，继续逐个“补页面”会重新陷入局部修补：Chat、人物世界、设置和工作区各自看似完整，但用户旅程之间缺少连续关系。产品体验总图与用户旅程的总边界见 [`product-experience-map-v1.md`](./product-experience-map-v1.md)；本合同只负责其中 Chat 主锚点的首次进入、持续聊天和任务工作三个关键状态。

本阶段继续只改 Playground。正式 Chat、人物世界、设置、会话、LLM、IPC 和生产数据不在本合同范围内。

Prompt / Runtime 边界：本轮只确认 UI 如何呈现任务生命周期；不修改生产 System Prompt、伙伴 Prompt、记忆注入、任务识别、工具调用或权限策略。后续真实接入必须让 Prompt / Runtime 通过结构化事件驱动这些状态，而不是让 UI 猜测模型文本。

## 2. 功能目标（What）

1. Chat Playground 候选提供六种可验收状态：初次进入、正在聊天、处理中、需确认、已完成、未完成。
2. Chat 候选在六种状态之间保持同一侧栏、输入区和页面骨架；状态变化只改变必要内容，不重新发明一套页面。
3. 处理中状态显式展示 Chat 与右侧工作区的关系，工作区仍通过正式 `ChatRightDock` + 隔离文件夹具渲染；其他任务结果状态留在对话内。
4. 需确认状态复用正式 `PermissionConfirmCard`，必须提供允许、拒绝和暂时返回对话的路径；允许回到处理中，拒绝进入未完成。
5. 已完成状态在 Chat 内给出结果摘要和继续聊天入口；未完成状态说明用户可理解的失败原因，并提供重试与回到对话。
6. 首次进入不出现“换主角”操作；角色架继续由设置中的角色架承载。
7. 为后续人物世界、设置和工作区的完整旅程验收留下统一的状态 / 上下文规则。

## 3. 技术方案（How）

- `SurfaceBaselinePanel.tsx` 的 `ChatSurface` 增加 Playground-only `journey` 状态和轻量分段入口；不写入 URL、localStorage 或生产设置。
- `ChatSurface` 的初次进入复用现有欢迎区；正在聊天使用静态用户 / 伙伴消息夹具；处理中在同一消息流中加入任务执行卡，并显式挂载 `ChatRightDock`。
- `ChatSurface` 的需确认、已完成和未完成状态继续复用同一消息流位置；需确认复用正式 `PermissionConfirmCard`，完成 / 失败使用轻量结果卡，不引入新的全屏层。
- 右侧工作区使用现有 `FILE_PREVIEW_FIXTURES` 与 `ChatRightDock` 的 `playgroundTabs` 隔离模式，不触发真实项目 IPC。
- 视觉仅使用现有 CSS token；状态切换采用已有 transition / `var(--motion-*)`，不为故事另造基础组件。
- E2E 证明六种旅程可切换、首页不展示换主角、只有处理中出现工作区、确认允许 / 拒绝可转移到对应状态、完成 / 失败可以回到对话且仍使用隔离夹具。

## 4. 影响范围评估

- 修改：Playground Chat 页面组合、Renderer E2E、产品体验施工合同、Progress、Changelog、Quality。
- 不改：正式 `App.tsx` Chat 运行逻辑、正式 Sidebar、正式 WorldHub / Moments 数据、LLM、IPC、会话持久化、生产设置。
- 风险：故事状态增加会提高候选页的可选项数量；通过将六态压缩为同一条 Chat 状态带、共享同一页面骨架，并让工作区只绑定“处理中”控制信息密度。
- 测试：必须运行 Unit、TypeScript、Renderer E2E、Build、Assets、Docs。

## 5. 实施步骤

1. 建立本合同，确认产品体验 E0 / E1 的边界与验收语言。
2. 在 Playground Chat 候选中加入六种任务生命周期状态与共享页面骨架。
3. 接入正式权限确认卡、隔离任务夹具和现有 Right Dock，不连接真实生产数据。
4. 补六种状态转换的 Renderer E2E 与边缘断言。
5. 更新 Progress、Changelog、Quality 和架构边界说明。
6. 完成自审、测试、构建、文档门禁；等待用户验收后再决定是否进入正式 UI。

## 6. 风险与权衡

- Playground 的静态消息和任务卡只用于确认密度、层级和上下文关系，不代表真实对话内容。
- 不在 Chat 空态增加人物切换、复杂状态说明或开发信息；降低首屏干扰优先于展示功能数量。
- 右侧工作区只在处理中任务旅程出现，避免把工作台永久变成 Chat 的第二主界面；需确认、已完成、未完成都不打开工作区。
- Prompt / Runtime 尚未接入本轮六态候选；正式接入时必须通过结构化事件映射状态，不能依赖 UI 对自然语言做脆弱解析。
- 本合同不提前决定正式 UI 的所有文案、真实任务卡数据和工作区自动出现策略；这些要在候选验收后根据真实用户旅程回流。

## 7. Phase E0 / E1 验收标准

- Playground Chat 候选可以在“初次进入 / 正在聊天 / 处理中 / 需确认 / 已完成 / 未完成”之间切换，六种状态共享同一侧栏、输入区和内容骨架。
- 初次进入只显示伙伴问候与开始建议，不显示“换个主角”；正式角色架入口仍在设置候选中。
- 正在聊天至少显示一条用户消息和一条伙伴回复，信息层级可读且不伪装成真实会话。
- 处理中显示任务执行状态，并出现隔离的 Right Dock；文件 / 预览仍来自 Playground fixture，不触发真实 IPC。
- 需确认显示风险、操作和批准范围，允许回到处理中，拒绝进入未完成；已完成显示结果摘要；未完成显示失败原因、重试和回到对话。
- 标准宽度和分栏窄宽均可切换；窄宽下内容不横向溢出或遮挡输入区。
- 用户确认前只改 Playground；正式产品默认行为和生产数据边界不变，Prompt / Runtime 生产资产不变。
