# Foundation 复用链路与自动门禁施工合同

> 状态：进行中（2026-09-13，范围与方案待确认，尚未开始代码施工）
> 生命周期：Phase P0；仅整改 Playground，正式回流必须另获许可。
> 来源：用户要求统一检查 Markdown 及其他产品体验控件，用工程化方式保证产品体验来自基础层。

当前进展补充：共享 TabStrip、CodeBlock、就近主题/Mermaid 与 DiffViewer 已在获批的 `playground-workspace-five-tools-v1.md` P1 范围实施。下表保留审计时证据，不作为这些片段的当前实现；整体四页面通用控件整改仍未完成，也未因共享片段回流而扩大本合同授权。

## 1. 背景与目标

当前“基础引用”主要是注册表声明，并不能证明页面实际渲染了同一份组件。基础故事通过验收后，产品体验仍可能漏传变体、重新画一个同名控件，或依赖另一套主题。

本次目标不是统一截图上的颜色，而是建立可执行的链路：基础实现及主题契约 → 同源故事 → 产品体验真实调用 → 静态门禁与浏览器回归。任何一环断开都不能宣称完成。

## 3. 完整施工边界

### 3.1 本次必须完成

- 覆盖 Chat、人物世界、设置、工作区四个 Playground 产品体验，以及设置内的记忆、权限、模型、Skills、MCP 等已存在子场景。
- 统一 Markdown、代码块、Mermaid 和差异查看器入口；覆盖工作区行内 / 并排 / 多文件审阅、文件预览、侧边聊天及其他实际 Markdown 使用方。
- 将已被这些体验使用的 Button、IconButton、Input、Textarea、Select、Checkbox、Switch、Tabs、通用反馈和相关展示基元收为真实基础实现；基础故事同步使用同一实现。
- 业务特有的确认流程、表单数据、角色卡、记忆条目、权限规则列表仍留在业务层，但其通用控件从基础层来。
- 补全实际依赖登记、源码门禁、负例测试和四主题视觉 / 行为验收；接入已有测试、资产检查及提交链路。
- 所有已确认的局部重复实现必须完成迁移；不能只修 Markdown 却把其他审计问题宣称已完成。

### 3.2 明确不做

- 不修改正式页面默认视觉、IA、数据保存、权限引擎、IPC 或 Agent 运行行为。
- 不把四个 Playground 候选主题加入生产七主题注册表，不写全局 DOM 或用户设置。
- 不引入整套新 UI 框架，不扩充尚未被产品体验使用的实验控件目录。
- 不禁止 div / span / section 等业务布局 HTML；不把业务组合伪装成基础控件。
- 不把第三方网页、代码示例或媒体本身的颜色当成应用皮肤违规；其嵌入边界仍需明确。

## 4. 技术方案

### 4.1 基础实现与业务组合

- 在 Playground 受控基础实现目录维护可复用组件；优先提取现有已验收行为和主题 token，不重新设计一套视觉。
- 基础层负责皮肤、尺寸规格、键盘语义、禁用 / 焦点 / 加载、复制与关闭操作槽；业务层传内容、状态、回调和布局意图。
- 不能用只透传任意 className / style 的包装器冒充统一基础实现。组件视觉参数通过受控变体表达，业务布局与基础皮肤分别校验。
- 现有生产组件需要隔离适配时，只增加明确可选的候选入口或适配层；默认输出不变，并补默认行为回归。
- 故事是基础组件的消费者，不是组件实现来源的第二份副本；没有消费者的 import 不计为复用证据。

### 4.2 Markdown 与差异

- 候选 Markdown 入口固定代码块策略、局部主题和安全策略；业务不得直接调用高亮库、Mermaid 或漏配的默认 Renderer。
- 语法颜色跟随就近主题，容器背景使用语义 token；内部背景透明，但不清除 Diff 新增 / 删除行、选区等有明确语义的高亮。
- 覆盖带语言 / 无语言围栏、未知语言降级、行内代码、长行、表格、链接、受控图片、aside、合法 / 非法 Mermaid。
- 差异查看器由同一基础实现提供行内与并排模式、空态及长文件呈现；业务仅传入文件及前后内容，不自行画第二套差异皮肤。不手写未经验证的差异算法。
- 保留现有链接 / 图片安全边界及 Mermaid strict 策略；错误提示不能泄漏内部堆栈。
- 复制按钮固定操作槽；失败显示可理解的反馈，不能静默吞错或让未处理 Promise 冒泡。

### 4.3 可验证的依赖登记

- 在现有注册表内区分基础实现的 module + export、故事使用方、体验入口和生产参考；不创建第二套手写组件目录。
- 使用已安装 TypeScript 的 AST / 符号解析检查引用，正确处理命名别名、转导出与包装组件；不使用只搜字符串的假依赖检测。
- 限定并发现 Playground 产品体验的实际入口与本地引用图；新增未归属组件必须失败，不能通过改文件名或藏进子目录逃过检查。
- usesFoundation 与真实可追溯使用证据交叉验证；只声明 key、只 import 不使用、复制一个同名本地组件，都不能通过。
- 已有生产组件以精确的只读隔离边界登记，不通过大范围 legacy / Playground 白名单豁免。
- 依赖元数据不得复制组件正文或主题颜色。候选主题仍使用 foundation-themes.ts 的单一事实源。

### 4.4 静态门禁

必须阻止：

1. 产品体验重新定义已收口的原生交互控件、另一套 Markdown / Diff / Switch 皮肤。
2. 绕过基础公共入口 import 第三方渲染器或旧候选配置路径。
3. 体验声明的基础依赖不存在、生命周期不兼容，或没有实际调用证据。
4. 基础故事不再引用对应基础实现，或只有未使用 import。
5. 业务给基础控件添加未受控的色值、皮肤覆盖或通过动态标签 / spread 绕开边界。
6. 新增候选文件未进入归属与引用图。

门禁输出具体文件、行号和原因。必须有“应失败”的违规 fixture 测试，包括别名、转导出、未使用 import、本地同名伪组件和越界样式；不能只证明当前代码通过。接入 npm run test 与 assets:check；不关闭现有 fail-closed 检查。

静态检查负责可枚举的工程约束，不声称可以证明所有运行时视觉正确；动态样式和渲染结果由浏览器测试补齐。

## 6. 实施与验收

以下是同一完整交付的验证顺序，不是“先交简版”的分期承诺。

1. 形成全部直接控件与被引用组件的分类清单，补充失败复现和负例 fixture。
2. 提取基础实现与局部主题契约，先让基础故事调用并通过基础测试。
3. 迁移所有本次范围内的体验调用方，移除重复皮肤，保留现有业务交互。
4. 注册表绑定真实实现与入口，开启源码门禁；确保预设违规会被拒绝。
5. 完整验收后再提交推送；机器通过后仍由用户验收 Playground，正式回流另获授权。

验收矩阵：

- 瓷青、曜石、松烟、绛紫；1166px 和 600px 视口；局部主题与全局主题交叉，不依赖根节点碰巧同色。
- 基础故事与体验同一组件的 computed style、实际背景、字体和几何关系一致。
- Markdown / Diff / Mermaid 的背景、长行、未知语言、错误恢复、主题切换及并发实例不串色。
- hover / focus / 已复制 / 删除确认等原位切换保持操作槽尺寸；长记忆编辑仍为多行，日期替换槽不回退。
- 记忆 CRUD、权限添加 / 取消 / 追加、Skills / MCP、模型配置、工作区五功能和人物世界导航全部保持可操作。
- 所有新点击只在隔离夹具内产生预期状态，不增加生产 IPC 或持久化写入。
- 原生布局标签、业务结构和第三方网页不会被门禁误判；真正的绕过样例必须失败。
- 自审 → Unit 与相关 UI → 类型检查 / build → 检查器语法与现有 lint 能力 → assets:check / docs:validate → 精确提交推送。

## 7. 风险与权衡

- 自动批量包一层组件会保留原有孤立皮肤：禁止以 JSX 标签替换数量作为成功指标。
- 简单文件依赖图会把共享文件的所有分支都算给每个体验：必须明确粒度和可解释证据，不伪造精确的组件使用关系。
- 过强门禁会禁止正常业务布局，过弱门禁会只检查字符串：以业务范围、符号解析、精确边界和正反例平衡。
- 局部主题不能依赖全局单例渲染配置：必须验证同时存在的不同主题实例。
- 当前生产组件存在历史视觉与行为：不得为了候选验收静默改变默认值。

## 8. 确认闸

用户已明确要求工程化整改方向；本合同将“其他都检查”具体化为以上四个体验、基础实现和门禁边界。由于这次不是单点修复，跨越组件所有权和验证机制，在用户确认本合同后开始代码施工。
