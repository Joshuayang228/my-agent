# Playground UI 控件分类与中英分层文案

> 状态：进行中（2026-08-13）

## 需求背景（Why）

Playground 需要同时承担三件事：一是确认 My Agent 的 UI 设计语言，二是帮助开发者理解常见前端控件术语，三是隔离验证 Prompt 与 Agent 交互实验。当前 UI 控件子分类已经能够承载按钮、输入、开关、卡片、导航和图标等故事，但分类命名、控件术语、Prompt 文案和代码标识的语言层级尚未明确，后续容易出现中文目录、英文组件名、双语 Prompt 和产品文案混写的问题。

本合同采用“UI 术语中文主名 + 英文辅助、Prompt 当前只做中文、代码保持原名”的分层规则：开发者可以在 Playground 学习常见 UI 英文术语，但生产 Prompt 不在本轮引入英文自然语言；未来英文 Prompt 版本另行翻译、审校和验收。

## 功能目标（What）

### 分类重组

Playground → 基础 → 基础组件使用以下中文分类：

```text
按钮
输入与选择
开关与设置行
徽标与标签
卡片与容器
导航与切换
图标
状态与反馈
快捷键与提示
```

约束：

- 分类导航只使用中文，不在分类标题后追加英文。
- 不使用“其他”作为长期垃圾桶分类。
- `EmptyState`、`Spinner`、`Progress`、`Skeleton`、`Alert`、`Toast` 等归入“状态与反馈”。
- `Kbd` 从“徽标与标签”中独立到“快捷键与提示”。
- `Card` 只描述容器形态；空态、错误态、加载态按状态归类。
- `Input` / `Select` 在当前规模下可以合并为“输入与选择”；当选择类组件明显增多时再拆分。

### 控件术语标注

只对常用、可迁移的 UI 控件和设计系统术语提供中英双语：

| 中文主名 | 英文辅助名 |
|---|---|
| 按钮 | Button |
| 输入框 | Input |
| 文本域 | Textarea |
| 下拉选择 | Select |
| 开关 | Toggle |
| 设置行 | ToggleRow |
| 徽标 | Badge |
| 标签 | Tag |
| 卡片 | Card |
| 导航项 | NavItem |
| 标签切换 | Tabs / PillTabs |
| 图标按钮 | IconButton |
| 加载指示器 | Spinner |
| 进度条 | Progress |
| 骨架屏 | Skeleton |
| 空状态 | EmptyState |
| 错误状态 | ErrorState |
| 快捷键提示 | Kbd |
| 分隔线 | Divider |
| 下拉菜单 | Dropdown |
| 确认框 | ConfirmDialog |
| 提示条 | Toast |

标注规则：

- 中文是标题、导航和说明的主语言。
- 英文使用低对比度灰色、小字号，作为学习辅助，不与中文争夺层级。
- 英文只用于常见控件名、组件名或稳定设计术语；不把所有状态、描述和句子都翻成双语。
- 状态和语义继续只用中文，例如“主要操作”“禁用”“加载中”“无数据”“搜索无结果”。
- 代码示例、组件 API、import 名称和注册表 canonical name 保持真实英文，不改成中文。

### Prompt 语言与结构分层

Prompt 遵循“当前中文、未来英文”的范围约束，并以“模型实际接收的语义”和“运行时结构”作为第一边界：

```text
先用中文写清楚意图与行为边界
        ↓
拆分稳定身份 / 动态上下文 / 行为策略 / 工具环境 / 协议契约
        ↓
只在必要处保留英文术语、代码标识或协议别名
```

参考 Alice 源码与本地分析资料（`_reference/alice-persona-world-source-analysis.md`、`_reference/alice-debug-mode-analysis.md`），采用以下思路：

- 稳定人格模板与动态插槽分离；不要每次动态变化都重写整份身份 Prompt。
- 按角色、用途和调用阶段维护 Prompt 映射；不要把主对话、压缩、生活世界、反思和工具说明揉成一个巨型字符串。
- 生活上下文、世界事实、用户关系和工具环境使用独立区块注入；每个区块有明确来源和生命周期。
- 可变人格、用户关系偏好和热更新覆盖与身份核心分离；修改可变块不能隐式改写稳定人设。
- Prompt 当前只维护简体中文版本；英文、多语言资产和按 locale 选择属于后续工作，不在本轮写入模型上下文。
- Prompt 可以预留国际化扩展点，但不以中英逐句对照、整段重复翻译的方式写入当前生产请求。

Prompt 编写顺序：

1. 先用简体中文写出行为意图、优先级、边界和例外。
2. 再标记必须保持原样的英文术语、工具名、JSON key、协议 token 或代码标识。
3. 如模型确实需要一个英文 canonical term，使用独立术语映射或括注一次，不重复写一份英文规则。
4. 最后通过 Prompt 语言测试和真实请求快照检查模型实际收到的内容。

禁止：

- 中英文逐句并排，导致同一规则出现两份且优先级不清。
- 为了“看起来专业”把中文行为规则改写成英文自然语言。
- 在 Playground 复制一份生产 Prompt 作为第二真相源。

### 图标体系边界

图标体系与 UI 控件并列：

```text
Playground → 基础
├── UI 控件
└── 图标体系
```

UI 控件中的图标只展示“图标如何被使用”；图标体系负责图标名、来源、尺寸、stroke、状态变体和复制代码。不得维护两套生产图标真相源。

## 技术方案（How）

### 目录与数据

- 扩展 `src/components/playground/catalog.ts` 的 UI 控件子分类定义。
- 必要时新增 `UiControlsSubId` 或独立图标体系 tab；旧故事 ID 只增不删，历史入口需要兼容或标记 archived。
- 常用控件的英文辅助名使用结构化字段维护，不把中英文直接散落在 JSX 文案中。
- 推荐字段：`labelZh`、`labelEn`、`descriptionZh`、`source`、`adopted`。
- 生产组件仍从正式组件目录 import；Playground 不复制生产皮肤。
- 图标生产源固定为 `lucide-react`；跨页面语义图标登记到 `src/shared/icon-registry.ts`，Playground 只展示该注册表的筛选目录，不复制 SVG 或引入第二套生产图标库。
- Prompt 实验只允许使用生产中文 Prompt 的显式隔离副本或会话级覆盖；实验文案不得自动回写生产 Prompt。英文翻译实验需等 wishlist 项目单独开工。

### 本轮落地（2026-08-16）

- 新增 `src/shared/icon-registry.ts`，登记导航、对话、开发、伙伴、资产和状态六类 Lucide 语义图标。
- Playground「基础 → 图标与视觉」提供中文主名、灰色英文名、稳定 key、用途和 P0 / P1 优先级的可搜索目录。
- 增加注册表 Unit 与 Playground UI E2E 验收；Alice 的 Tabler 图标仅作为参考，不进入生产依赖。

### UI 组件资产目录落地（2026-08-17）

- 新增 `src/shared/ui-component-registry.ts`，登记行为、状态、开发工具、伙伴世界和布局导航组件。
- 采用状态固定为 candidate / playground / adopted / deprecated / archived；已采用项必须指向真实源码，Radix 等外部来源只作为未安装候选。
- Playground「基础 → 基础组件」支持搜索、分类和采用状态筛选，并展示中文主名、灰色英文术语、故事数量与无障碍约束；无障碍验证状态独立登记，专项复核见 WISH-022。
- 图标分类导航保持中文单语；英文辅助只用于具体常用组件与图标名称。

### 视觉与交互

- 英文辅助名统一使用 `var(--text-muted)` 或同等级低对比度颜色，并使用小字号。
- 分类导航保持中文、短、稳定；窄屏时允许横向滚动或折叠，但不得出现标题遮挡。
- 组件故事至少展示默认态和一个边缘态；需要时展示 hover、active、disabled、loading、error、empty。
- 图标故事需要展示推荐尺寸阶梯和 stroke 约束；不要把所有外部图标库无筛选地导入生产。
- 深色和浅色主题都必须检查英文辅助名的可读性。

## 影响范围评估

- 破坏性：主要是 Playground 目录和展示文案调整；不改变生产组件 API、Prompt、会话、设置或自动 Eval。
- 兼容性：现有 Playground 故事 ID 不删除；分类重命名需要同步 UI E2E 断言和文档。
- 依赖：优先复用当前 `lucide-react` 和项目已有正式组件；是否引入额外图标库必须另行说明并在依赖变更前确认。
- 测试：补充分类注册表与双语字段单测；UI E2E 验证中文分类、英文辅助名、图标体系入口和窄屏可用性；Prompt 改动补跑语言门禁和真实请求快照检查。
- 文档：完成后更新 Playground 合同状态、`docs/progress.md`、`docs/changelog.md`；若形成新的长期 UI 规则，保持本合同为长期参照。

## 实施步骤与验收

1. 更新目录模型，完成中文分类和常用控件双语元数据。
2. 调整 UI 控件面板标题、描述和故事分组；将“其他”改为“状态与反馈”，分离快捷键提示。
3. 建立图标体系入口或独立设计 tab，先收录项目真实使用的图标，不追求一次性收录全量库。
4. 补充单元测试和 UI E2E；检查英文辅助文字的颜色、大小、主题适配和窄屏布局。
5. 更新文档并完成自审、测试、Build 和提交。

验收标准：分类导航全部为中文；常用控件标题显示中文主名与灰色英文辅助名；状态描述保持中文；当前生产 Prompt 只使用中文自然语言，英文仅保留必要技术术语、协议别名和代码标识，不出现中英逐句混写；未来英文 Prompt 另行立项；代码标识、组件名、API 与协议字段保持英文；UI 控件和图标体系职责清晰；Playground 试验不会写入真实会话、设置或生产资产。

## 风险与权衡

- 双语范围过大会造成视觉噪音，因此只覆盖常见、可迁移的控件术语。
- 中英文直接写在同一字符串里会导致未来翻译困难，因此使用结构化字段而不是散落拼接。
- 图标库越大，选择成本和包体风险越高；先收录真实使用集合，再按需求扩充。
- 分类调整会改变开发者寻找入口的习惯，保留稳定故事 ID 和旧入口兼容，降低迁移成本。
