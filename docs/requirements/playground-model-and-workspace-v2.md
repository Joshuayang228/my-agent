# 施工合同：模型与工作区用户故事重构 v2

> 状态：进行中
> 生命周期：进行中
> 范围：P0 Playground 候选；取得用户明确回流许可前，不修改正式 Settings、IPC、存储、Runtime 或真实模型连接。
> 研究参考：DSH `d347e703`、CC-Switch `db41d70`、Alice `0.3.168`

## 1. Why

当前模型页把 Provider、连接字段、模型 ID、用途和运行参数放在同一层。用户无法回答三个基本问题：我已经添加了什么、现在真正使用什么、修改设置会不会影响正在进行的任务。现有生产数据也只有一个主连接、一个主模型和一个辅助模型，页面不能提前伪装成已经支持多 Provider 运行时。

本合同以真实用户故事重新组织模型页和工作区：设置负责长期默认安排，工作区负责当前任务事实；连接、模型清单、使用安排和任务快照分别表达，不互相冒充。

## 2. What

### 2.1 模型页用户故事

1. 没有配置时，我只看到“添加连接”，不会被一整页 Provider 和模型字段打扰。
2. 添加第一个连接时，我可以选择预设、自定义连接或中转 / 网关，再填写真实的 Base URL、密钥状态和模型 ID。
3. 添加第二个连接后，我能区分两个连接，并知道哪个模型承担聊天、哪个承担辅助任务；第二个连接不会自动抢走当前默认模型。
4. 打开一个连接时，我能看到它的连接状态、模型清单、启用状态和用途；未打开的连接只保留摘要。
5. 我修改默认模型时，页面明确告诉我这是下一次任务的默认安排，而不是正在运行的任务。

### 2.2 工作区用户故事

1. 没有任务时，工作区不显示模型设置。
2. 任务开始后，工作区显示任务名称、来源、当前状态和本次任务启动时的模型。
3. 任务等待确认、审阅文件或执行终端时，我看到对应内容，不重复整套模型配置。
4. 任务完成时，结果回到 Chat；失败时，看到失败原因、没有修改什么、重试和回到对话。
5. 任务进行中修改默认模型，不改变当前任务的模型快照。

## 3. How

### 3.1 模型四层数据语义

```text
连接配置
  ↓
模型清单
  ↓
使用安排
  ↓
任务运行快照
```

| 层 | 表达什么 | P0 展示 |
|---|---|---|
| 连接配置 | 从哪里访问模型 | 名称、Provider、Base URL、密钥状态、连接状态 |
| 模型清单 | 连接下有哪些模型 | 模型 ID、启用 / 停用、模型数量 |
| 使用安排 | 哪个模型承担什么工作 | 聊天模型、辅助任务、沿用聊天模型 |
| 任务快照 | 本次任务实际用了什么 | Provider、模型 ID、启动时间 |

当前真实用途只展示“聊天模型”“辅助任务”“暂不使用”。模型发现、能力探测、故障转移、记忆模型和图像模型属于后续合同，不在 P0 伪造。

### 3.2 模型页结构

```text
当前使用
├── 聊天模型
└── 辅助任务

已添加连接
├── 连接摘要行 × N
└── 仅展开一个连接
    ├── 连接详情
    ├── 模型清单
    └── 使用安排

运行偏好
└── 采样参数与预算折叠区
```

添加流程独立于已添加列表：来源选择 → Provider / 自定义地址 → 连接详情 → 模型 ID → 用途 → 保存。Provider 预设只能填入口信息，不得写死模型 ID。

### 3.3 工作区状态矩阵

| 状态 | 工作区 | 模型信息 | 主动作 |
|---|---|---|---|
| 无任务 | 不出现 | 不出现 | 回到 Chat |
| 处理中 | 出现 | 显示任务快照 | 查看文件 / 预览 / 终端 |
| 等待确认 | 出现 | 保留快照 | 批准 / 拒绝 |
| 待审阅 | 出现 | 保留快照 | 查看变更 |
| 已完成 | 收起或回到 Chat | 不重复设置 | 查看结果 |
| 未完成 | 保留恢复入口 | 区分模型错误与文件 / 权限错误 | 重试 / 回到 Chat |

任务开始时固定 `profileId`、`provider`、`modelId`、`startedAt`。设置变化只影响下一次任务。

## 4. 参考取舍

- DSH：采用“已添加 Provider 列表、一次编辑一个、模型选择器和统一状态快照”。不复制其插件生态和 Provider 目录规模。
- CC-Switch：采用“添加来源分流、预设 / 自定义、手动模型 ID + 获取后选择”的交互结构。不复制其多应用路由、用量和故障转移复杂度。
- Alice：采用“Provider 与模型 ID 分离、模型清单可选择、能力状态可解释”。当前没有真实探测链，因此只做隔离样张。

## 5. 边界

- P0 只改 `src/components/playground/SettingsExperienceCandidate.tsx`、`src/components/playground/SurfaceBaselinePanel.tsx` 及隔离测试。
- 不改 `src/components/SettingsPanel.tsx`、`src/App.tsx`、`electron/main/*`、真实设置存储、LLM 工厂、IPC 或凭据。
- Playground fixture 不调用 `window.electronAPI`，不展示真实 API Key，不发起模型请求，不写入会话或任务。
- 正式回流必须另行取得用户明确许可，并按 `playground-to-production` 流程执行。

## 6. 实施步骤与验收

### P0-1 合同与研究收口

固定本合同、参考仓库版本和真实生产边界。

验收：合同索引可发现；模型页和工作区的职责不重叠。

### P0-2 模型候选

实现空态、单连接、双连接、连接详情、模型清单、使用安排和添加流程样张；所有状态由 Renderer 内存驱动。

验收：用户能明确说出“当前使用什么”“已添加什么”“这个模型为何启用”。

### P0-3 工作区候选

实现无任务、处理中、等待确认、待审阅、完成和失败状态；显示任务模型快照，错误按模型 / 文件 / 权限区分。

验收：切换状态不会复制模型设置；完成和失败都能回到 Chat。

### P0-4 自动化与人工验收

补充 E2E，检查宽屏 / 窄宽、溢出、键盘操作、深浅主题和“不触发真实 IPC”。用户在 Playground 验收后，才进入 P1 正式回流。

## 7. 风险与权衡

- 生产只有单连接模型，P0 多连接只是未来数据结构的视觉验证；必须标注“仅供预览”。
- 模型自动发现很容易被误解为真实可用；没有真实请求链时只展示选择流程，不宣称已获取模型。
- 工作区若复制设置会造成任务状态和默认设置混淆，因此只展示运行快照。

## 8. 完成判定

Playground 同时具备模型四层结构、六种工作区状态、可解释的空态 / 添加态 / 多配置态和隔离测试；正式页面、Runtime、存储和 IPC 均未被本合同提前修改。
