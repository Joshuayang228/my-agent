# 施工合同：模型与工作区解耦重构 v2

> 状态：进行中
> 生命周期：进行中
> 范围：先完成 Playground 候选与合同对齐；取得用户明确回流许可后，再回流正式 Settings、Chat、Runtime、IPC 与存储。
> 研究参考：DSH `d347e703`、CC-Switch `db41d70`、Alice `0.3.168`

## 1. Why

当前模型页把“连接从哪里来”“连接下有哪些模型”“模型承担什么用途”混在一套表单里。用户需要在添加一个中转站时同时填写“第一个模型 ID”和“主对话 / 辅助任务 / 生图”，导致三个概念互相耦合：

- 一个连接通常对应多个模型，不能用一个“第一个模型 ID”代表它；
- 同一个模型可以被安排给不同用途，模型本身不应该携带用途；
- 用户可能同时使用官方服务商、中转站、聚合平台、统一网关或本地模型，页面必须让连接来源和最终使用安排分别可理解；
- 连接下的模型清单需要支持从远端获取，也要支持远端不提供列表时手动添加；
- 主对话、辅助任务和生图需要独立的有序路由，不能再用“辅助任务沿用主对话模型”掩盖没有配置；
- 正在运行的任务必须固定启动时的模型，不能因为用户修改默认安排而中途漂移。

本合同把模型页拆成两个上下分区：

1. **上方：模型使用安排**，从已添加的连接模型中选择不同用途的候选，并用顺序表达优先级；
2. **下方：连接管理**，维护连接本身及其模型清单，不关心模型被分配给哪种用途。

工作区仍单独负责当前任务事实，不成为第二个模型设置页。

## 2. What

### 2.1 模型页用户故事

1. 没有连接和模型时，我先看到清晰空态和“添加连接”，不会看到一整页无上下文的 Provider、模型用途和参数。
2. 添加连接时，我可以选择官方服务商、中转 / 聚合 / 统一网关、本地模型或自定义连接；这些都是连接入口，不把“米羊”之类具体平台硬编码成连接类型。
3. 自定义连接时，我选择项目已经支持的适配器：OpenAI Compatible、Anthropic 或 Gemini；适配器表示协议，不等同于渠道名称。
4. 保存连接后，我可以在该连接下维护多个模型：点击“获取已有模型”从连接端点读取列表，逐项选择添加；获取失败、不支持或返回异常时，可以手动添加模型 ID。
5. 我打开一个连接时能看到连接名称、适配器、Base URL、密钥状态、连接测试状态和模型清单；未展开的连接只显示摘要和模型数量。
6. 我在页面上方分别配置主对话、辅助任务、生图。每种用途都可以添加多个已登记模型，顺序就是优先级，第一项不可用时按顺序尝试下一项。
7. 我可以拖动调整优先级、暂时停用一个路由项、删除一个路由项；这些操作不删除连接下的模型清单。
8. 同一个连接模型可以出现在多个用途中，但每个用途的排序和启用状态独立保存。
9. 我能看到当前安排将影响后续任务；正在运行的任务不会被新的默认安排改写。
10. 对话输入区和消息详情会显示本次实际使用的“连接名称 · 模型 ID”；发生故障转移时，显示已切换到哪个备用模型，但普通对话不默认展开完整调试信息。

### 2.2 工作区用户故事

1. 没有任务时，工作区不显示模型设置，也不要求用户理解“业务状态”这类内部术语；页面标题使用用户能理解的“任务工作区”。
2. 任务开始后，工作区显示任务名称、来源、当前状态和本次任务启动时固定的模型快照。
3. 任务等待确认、审阅文件或执行终端时，我看到对应内容，不重复整套连接和模型安排。
4. 任务完成时，结果回到 Chat；失败时，我能区分模型不可用、网络 / 连接失败、文件错误和权限错误，并看到重试或回到对话的入口。
5. 任务进行中修改模型使用安排，不改变当前任务的模型快照。

## 3. How

### 3.1 数据与职责分层

```text
连接配置
  ↓
连接下的模型清单
  ↓
用途模型路由（主对话 / 辅助任务 / 生图）
  ↓
任务运行模型快照
```

| 层 | 表达什么 | 允许做什么 | 不表达什么 |
|---|---|---|---|
| 连接配置 | 从哪里访问模型、使用哪种协议 | 名称、适配器、Base URL、凭据引用、启用状态、连接测试 | 主对话 / 辅助任务 / 生图 |
| 模型清单 | 这个连接能被用户选择的模型 ID | 获取、手动添加、编辑、去重、启用 / 停用、删除、排序 | 模型用途和全局优先级 |
| 用途模型路由 | 某类任务按什么顺序尝试哪些模型 | 主对话、辅助任务、生图分别多选、排序、停用、移除 | 连接凭据和模型发现过程 |
| 任务运行快照 | 本次任务真正采用的候选和实际模型 | 固定用途、候选顺序、实际尝试、成功模型、启动时间 | 修改默认设置 |

模型清单项至少需要能稳定引用 `connectionId + modelId`。用途路由保存有序引用和启用状态，不复制 Base URL、API Key 或适配器。运行时快照保存任务启动时解析出的连接、适配器、模型 ID、用途、候选顺序和时间，避免设置变化导致任务漂移。

### 3.2 连接入口与适配器

连接管理的连接类型只用于说明入口来源和表单行为：官方服务商、中转 / 聚合 / 统一网关、本地模型、自定义连接。

“中转”“聚合”“统一网关”在模型配置中统一作为连接入口管理，不为每个平台单独造一套模型页。连接名称由用户填写，例如“OpenRouter”“国际流动”“公司统一网关”；产品不内置与业务无关的平台名称。

适配器是协议层选择，当前使用已有的三个适配器：OpenAI Compatible、Anthropic、Gemini。连接类型和适配器必须在数据上分开：同一种适配器可以服务多个渠道，同一个渠道也不能因此被误认为官方 Provider。

### 3.3 连接下的模型清单

连接详情区域只做连接信息和模型清单管理，不出现用途下拉框：

```text
连接名称       DeepSeek
适配器         OpenAI Compatible
Base URL       https://api.deepseek.com
API Key        已配置 / 未配置

模型清单       2 个已添加
  deepseek-chat       已启用   [编辑] [移除]
  deepseek-reasoner   已启用   [编辑] [移除]

  [获取已有模型]      [手动添加模型]
```

“获取已有模型”参考 CC-Switch 与 Alice 的交互：

1. 用户先填写连接需要的端点和凭据引用；未满足前置条件时按钮禁用并说明缺什么。
2. 用户点击“获取已有模型”，按钮立即进入加载状态，防止重复请求。
3. 后端按照适配器构造模型列表请求。OpenAI Compatible 默认请求端点的 `/v1/models`；Base URL 已包含版本路径时不得重复拼接。Anthropic、Gemini 和本地端点使用各自适配器的模型列表契约；不支持列表时返回可理解的失败原因。
4. 返回成功后，展示可搜索、可勾选的远端模型列表，并标记已经添加的模型，避免重复添加。用户确认后才写入本连接的模型清单。
5. 返回 401 / 403、404 / 405、格式不符合预期、超时或网络错误时，页面说明原因和补救动作，并保留“手动添加模型”路径。
6. 获取模型只是发现模型 ID，不等于能力探测；不能因为列表返回了某个模型就宣称它支持文本、图片、工具或思考能力。能力探测属于连接测试 / 运行时策略的独立链路。

手动添加模型用于远端不支持 `/models`、模型列表不完整、用户使用私有模型 ID或需要提前登记尚未公开的模型。手动添加只要求模型 ID，不能再出现“第一个模型 ID”或“模型用途”字段。

模型清单的排序只表示该连接内的整理顺序；跨连接的故障转移优先级只在上方的用途模型路由中表达。

### 3.4 模型使用安排

模型页顶部改为可编辑的“模型使用安排”，不再是只读“当前使用”样张：

```text
模型使用安排

主对话
  1  OpenAI 主账号 · gpt-4o                 [启用] [拖动]
  2  DeepSeek · deepseek-chat                [启用] [拖动]
  + 添加模型

辅助任务
  1  DeepSeek · deepseek-reasoner             [启用] [拖动]
  + 添加模型

生图
  1  图像连接 · image-model-id               [启用] [拖动]
  + 添加模型
```

约束：

- 三种用途完全解耦，不在连接模型行上出现用途下拉框；
- 每种用途从已启用的连接模型中多选，选择项必须显示连接名称和模型 ID；
- 同一模型可被多个用途引用，但每个用途保存自己的优先级和启用状态；
- 路由顺序就是 fallback 顺序；运行时在当前项发生可重试的连接 / 网络 / 限流 / 服务端失败时，按顺序尝试下一项；鉴权配置错误等不可通过换模型解决的错误要明确终止并提示修复连接；
- 没有配置时显示“还没有安排模型”和对应的添加动作，不暗示自动沿用其他用途；
- 生图是独立用途，即使当前 Chat 尚未展示生图入口，设置数据结构和 UI 也不能把它并入主对话；
- 路由修改影响后续调用，不覆盖已创建的任务快照；
- 选择器只展示已登记的连接模型。若连接或模型被停用，已存在的路由项显示为不可用并提供替换 / 移除动作，不静默改成另一个模型。

### 3.5 Chat 展示与运行时证据

上方配置的模型如果存在有效路由，应在 Chat 的低干扰位置出现：

- 输入区显示当前主对话路由的首选“连接名称 · 模型 ID”，可以打开菜单查看备用顺序；
- 用户主动切换时，只改变当前会话允许使用的路由范围，不修改连接清单；具体是否持久化为默认安排，需由正式 Settings 交互另行确认；
- Assistant 消息详情显示实际用途、连接、模型和尝试顺序；
- fallback 发生时，在消息或状态提示中说明“已切换到备用模型：连接 · 模型”，不暴露堆栈、请求头或凭据；
- 普通对话默认保持简洁，完整调用证据仍归 Debug / 任务详情，不把内部日志塞入每条消息。

### 3.6 工作区模型快照

任务创建时从用途路由解析并固定：

```text
taskId
purpose
candidateRoutes[]
actualConnectionId
actualAdapter
actualModelId
startedAt
fallbackEvents[]
```

工作区展示“本次任务使用：连接名称 · 模型 ID”，以及必要的备用切换记录。它不提供连接编辑、模型获取或用途排序，避免与模型页形成第二事实源。

### 3.7 前端候选与真实后端边界

本合同分两阶段，但每个阶段都必须是可独立验证的完整交付：

- **P0 Playground 候选**：用隔离 fixture 展示连接清单、多个模型、获取已有模型的加载 / 成功 / 空结果 / 不支持 / 认证失败 / 网络失败状态、用途多选与拖动排序、fallback 预览、Chat 展示和工作区快照。候选中的获取动作必须明确标记为“样张 / 隔离实验”，不能伪装成真实请求；不得调用 `window.electronAPI`、写设置、写会话或写任务。
- **P1 正式能力**：在用户明确许可回流后，实现共享类型、设置存储、preload、IPC、适配器模型列表请求、凭据安全读取、模型清单持久化、用途路由持久化、运行时有序 failover、Chat 证据和工作区快照。真实“获取已有模型”必须走后端，不允许前端直连供应商。

## 4. 参考取舍

- **CC-Switch**：采用其“先填连接信息，再获取模型；远端列表按类别选择；不支持获取时保留手动模型 ID”的交互。采用连接下多个模型、编辑 / 删除和列表管理思路；不复制其多应用同步、用量统计和插件生态。
- **Alice**：采用其 `provider:fetchModels` 的前后端边界、按适配器构造 `/v1/models` 或对应模型列表请求、端点和超时错误处理，以及 Provider 与模型 ID 分离的配置方式；不把 Alice 的平台命名或产品语义直接搬进本项目。
- **DSH**：采用“连接摘要、一次编辑一个连接、状态快照”的信息密度；不复制其与本项目人格化伙伴无关的 Provider 目录和业务流程。

## 6. 实施步骤与独立验收

### P0-1 合同与参考研究收口

更新本合同，固定四层数据语义、C-Switch / Alice 的模型获取交互和 P0 / P1 边界。

验收：合同索引可发现；全文不再把用途配置放在连接下，不再把模型获取、fallback、生图写成“以后再说”的冲突描述。

### P0-2 连接与模型清单候选

实现空态、单连接、多连接、展开详情、多个模型、编辑 / 删除、获取已有模型的加载 / 成功 / 空结果 / 错误状态和手动添加路径。

验收：用户能明确区分连接名称、适配器、模型 ID和连接内排序；获取失败时仍有可用的手动添加动作；候选不触发真实 IPC。

### P0-3 用途模型路由候选

实现主对话、辅助任务、生图三个独立区块；支持从已登记模型多选、拖动排序、启用 / 停用、移除、空态和 fallback 顺序预览。

验收：同一模型可跨用途引用；用途变化不会改变连接清单；页面不出现“沿用主模型”的隐式配置。

### P0-4 Chat 与工作区候选

实现 Chat 中首选模型 / 备用模型的低干扰展示、fallback 提示和消息详情；实现工作区无任务、处理中、等待确认、待审阅、已完成和未完成状态，并展示固定模型快照。

验收：切换设置不改当前任务；工作区不复制连接编辑；完成和失败都能回到 Chat。

### P0-5 隔离验收

补充宽屏 / 窄宽、深浅主题、文本溢出、键盘操作、重复点击、加载 / 空 / 错误 / 取消路径的测试与截图验收。

验收：所有候选交互可达且有明确反馈；不产生真实设置、会话、任务或模型请求副作用。用户明确说“可以回流 / 就这样改正式页面”后，才进入 P1。

### P1-1 后端模型获取与连接模型清单

按现有四处 IPC 契约接入 `fetchModels` 能力。主进程根据适配器构造请求，安全读取凭据，处理认证、端点不支持、响应格式、超时和网络错误；前端只消费结构化结果。成功获取的模型在用户确认后写入连接模型清单，手动添加走同一清单接口并去重。

验收：至少覆盖 OpenAI Compatible 的 `/v1/models`，并为 Anthropic、Gemini、本地 / 自定义适配器保留明确的能力结果或“不支持获取、请手动添加”错误；没有 API Key 时不会发起请求；真实错误不会泄露凭据或内部堆栈。

### P1-2 用途路由、fallback 与快照

持久化三类用途的有序路由，接入运行时顺序 failover，区分可重试错误和必须修复连接的错误，在任务创建时生成不可变快照。

验收：第一候选失败时可按顺序尝试下一候选；路由顺序、实际成功模型和 fallback 事件可追溯；正在运行任务不受设置修改影响。

### P1-3 Chat / 工作区正式回流

将候选中的展示规则回流到正式 Chat、Settings 和工作区；补齐深浅主题、窄宽、长模型 ID、省略与展开、键盘和无障碍行为。

验收：用户能在不打开 Debug 的情况下知道当前实际使用的连接与模型；需要诊断时可在消息详情或 Debug 查看尝试顺序和错误分类。

## 7. 风险与权衡

- **不同适配器的列表契约不一致**：P1 先以适配器返回结构化结果；不支持列表的适配器必须清楚降级到手动添加，不能伪造统一成功。
- **获取到模型不代表具备某种能力**：模型发现与能力探测分开，避免用户看到模型后误以为一定支持生图、工具或视觉。
- **fallback 可能导致成本或行为变化**：路由顺序明确可见；发生切换时告知用户；鉴权错误等不可重试错误不盲目切换。
- **同一模型跨用途引用**：连接模型清单是单一来源，路由只保存引用，避免编辑一个模型后留下多份凭据和端点副本。
- **长模型 ID造成布局溢出**：使用稳定列宽、可展开完整值和省略策略，禁止截断到无法识别的程度。
- **当前生产类型仍是单主模型 / 单辅助模型**：正式回流需要兼容旧设置或进行明确迁移；迁移方案、旧字段保留周期和失败回滚在 P1 开工前补入实现说明，不在 P0 fixture 中假装已迁移。

## 8. 完成判定

本合同对应的候选完成时，必须同时具备：

- 连接配置、连接模型清单、用途模型路由、任务运行快照四层语义；

- 主对话、辅助任务、生图三种用途的独立多选、优先级、启用 / 停用和 fallback 预览；
- Chat 的实际模型与 fallback 展示；
- 工作区六种状态及固定模型快照；
- 获取已有模型的加载、成功、空结果、不支持、认证失败、超时和网络失败状态；
- 深浅主题、窄宽、长模型 ID、键盘和隔离副作用测试；
