### 参考证据与问题根因

- Alice 提取源码 `_reference/framework-harness/repos/alice-source/_extract/index-ppRSWnkN.js`：`ZM` 定义六组、26 个入口，默认 `promptManager`；提示词页占满剩余高度并分别滚动目录与详情，其他页使用阅读布局。

日记、信件、生活账簿、头像 / 封面历史及用户待办在对照矩阵和缺口账本中保留；未经数据模型施工，不加入假装可用的正式页面。动态兴趣与行动账本也不由静态兴趣 / Trace 冒充。候选允许显示明确的能力缺口说明，但不得出现没有逻辑的操作按钮。

每页结构固定为：标题 / 范围与数量 → 人物 / 日期等适用筛选 → 对象列表 → 详情及来源 → 关联证据；字段不存在、数据为空、读取失败和未支持必须分别表达。长目录与长正文独立滚动；窄屏通过列表 / 详情切换维持可读性，不强塞三个窄栏。

### 真正需要补的数据契约与边界

1. 今日日程：保留角色、日期、时区、生成来源和截断标记；按 slot / event 显式标识关联。现有 planned / published 不增加假的「完成」「跳过」。完整执行、取消、重排原因需在生产事件模型实现后展示。
2. 生活资产：`companion:get-assets` 调用 `ensureStarterAssets`，存在初始化副作用。Debug 新读取路径使用纯只读查询，不以普通浏览偷偷播种资产；新增 IPC 须同步四处。
3. 人物记忆：当前世界快照读取全局 memories，不适合作为「当前人物专属记忆」事实源。按 role 与共享范围形成明确契约后接线，不在 Renderer 靠文案推断归属。
4. 历史与截断：现有快照只返回最多 12 时段、30 事件、10 动态、20 记忆及截断正文；首次候选不能把样张总数写成全量生产总数。完整历史需有界查询、分页及明确范围。
5. 用户任务：定时任务、Agent 在途任务与用户待办各自有不同生命周期，保持分开；不复用定时任务成功状态证明用户完成事项。
6. 只读与受控动作：Prompt 编辑、强制反思、重生成日程、切换头像和消费等均不随 Alice 页面自动移植。默认浏览不得调用模型、写配置、写人物状态或触发资产初始化。

## 1. 需求背景（Why）

当前项目已经具备正式 Debug 的真实数据链路：Prompt、生产资产、LLM 请求、Trace、Event、伙伴世界快照、Eval、系统信息和工具目录。但 `DevPanel` 仍以功能面板集合为主，用户需要在多个分区之间自行拼接一次运行的上下文，难以快速回答“系统现在是什么”和“刚才为什么这样运行”。

Debug 不应成为第二个 Settings，也不应复制 Playground 的实验控制器。它需要把真实运行事实、证据明细和受控诊断动作分层表达，并保持真实 IPC、脱敏和只读边界。

## 2. 功能目标（What）

1. 让 Debug 默认入口先呈现当前运行概览，而不是直接落入某个内部面板。
2. 将真实运行状态与证据明细分层，支持从资产、LLM 调用、Trace、Event 之间定位关联。
3. 保留现有 Prompt、伙伴状态、Eval、系统信息和工具能力，不因重排 UI 丢失真实数据入口。
4. 明确只读信息、受控诊断动作和禁止进入 Debug 的 Settings / Playground 能力。
5. 对长文本、加载、空态、错误、脱敏、窄宽和键盘操作建立统一验收标准。
6. 让每个 UI 数据块都能追溯到真实组件、IPC 或主进程聚合器。

## 3. 技术方案（How）

### 3.1 三层信息模型

```text
运行概览
├── 当前会话 / 当前任务
├── 当前模型与运行预算
├── Prompt / 记忆 / 工具摘要
└── 当前错误与运行状态

真实证据
├── Prompt 与生产资产
├── LLM 请求与响应摘要
├── Trace 调用链
├── Event 时间线
├── 伙伴 / 世界快照
└── Eval 报告

受控诊断
├── 刷新真实状态
├── 运行受限诊断
├── 导出脱敏报告
└── 清理或归档调试日志
```

### 3.2 真实数据边界

- UI 只消费 `window.electronAPI.debug` 和已有事件流，不在 Renderer 推断生产事实。
- Prompt、资产、模型、工具、权限和 MCP 状态必须来自对应主进程聚合器或正式 IPC。
- 用户 API Key、Prompt 隐私正文、原始请求秘密和内部文件路径继续遵守现有脱敏规则。
- Playground fixture、故事注册表、来源路径和实验控制器不得进入正式 Debug 默认视图。
- 受控动作若新增 IPC，必须在主进程重新校验输入、权限、取消和审计，不得仅依赖 Renderer 隐藏按钮。

### 3.3 关联模型

一次运行的概览、LLM 请求、Trace 和 Event 应尽量使用稳定的会话 / 任务 / span 标识关联。若现有数据无法支持某种关联，先展示明确的“未关联”状态，不在 UI 中猜测关系；需要补充跨层标识时另行扩大施工范围。

## 4. 影响范围评估

### 4.1 预计修改

- `src/components/DevPanel.tsx` 及 `src/components/debug/` 的页面组合和展示层；
- 必要的 Debug 共享类型和只读数据适配；
- 正式 Debug 的 Renderer E2E 与相关 Unit；
- 本合同、质量门禁、进度和变更记录。

### 4.2 默认不修改

- Agent Loop、Prompt 正文、Provider 路由和模型行为；
- 权限规则、凭据存储、记忆写入和正式设置保存；
- Playground 候选、fixture 和 Playground 导航；
- 现有 Debug IPC 的语义。

### 4.3 升级条件

如果实现需要新增或修改 IPC、日志存储、权限判断、跨模块事件标识、Prompt / 资产聚合契约或运行时状态模型，必须先更新本合同技术方案和影响范围，再开始对应代码施工。

## 5. 实施步骤

1. **现状映射**：建立 Debug 分区、组件、IPC、主进程来源和现有测试的映射表。
2. **信息架构候选**：只在 Debug 设计候选中验证运行概览、证据明细和受控动作的层级，不改变真实数据。
3. **用户验收**：确认默认入口、分区命名、信息密度、状态表达和关键跳转。
4. **正式 UI 实施**：在 `DevPanel` 和正式 Debug 子组件中选择性重排，保持现有 IPC 和数据边界。
5. **行为验证**：补齐正式入口、数据加载、错误、空态、脱敏、关联跳转、深浅主题、窄宽和键盘 E2E。
6. **受控动作评估**：只有有明确用户价值且能完成主进程校验、取消和审计的诊断动作才进入实现；其余留在只读展示。
7. **文档收口**：更新质量门禁、进度、变更日志和受影响模块卡；确认资产目录仍只登记真实生产来源。

## 6. 风险与权衡

- 运行概览可能重复 Settings 内容，必须展示“当前实际状态”，不能展示“用户默认设置”。
- 证据明细容易退化成原始 JSON，优先提供可读摘要、时间线和关联跳转，原始内容只作为受控展开。
- Debug 的诊断动作可能产生费用、写入日志或改变运行状态，默认只读，新增动作必须单独评估风险。
- Alice 的分组方式只能作为信息架构参考，不能替代本项目的 IPC、脱敏和权限契约。
- 如果现有 Trace、LLM 和 Event 缺少共同标识，不为视觉上的“统一时间线”伪造关联。

## 7. 必测点

- 默认进入 Debug 时能看到运行概览，并能进入真实证据明细；
- 每个展示区能定位到真实数据来源；
- LLM、Trace、Event 之间的关联存在时可跳转，不存在时明确说明；
- Prompt、资产、模型、工具、权限和 MCP 信息不泄露凭据或不必要的内部细节；
- 加载、空态、错误、长文本、窄宽、深浅主题和键盘焦点可用；
- 刷新失败不会清空已有可用证据，且错误可理解；
- Debug 不写入 Settings、记忆、会话或 Playground fixture；
- 任何受控诊断动作都有主进程校验、取消 / 失败反馈和审计证据；
- Playground 与正式 Debug 的边界没有被 UI 复用意外打穿。

## 8. 完成判定

在用户确认信息架构候选、正式 Debug 入口和真实证据映射成立前，本合同不得进入正式 UI 实施。完成后，必须满足：正式 UI 仅展示真实生产事实；测试覆盖关键状态和安全边界；文档已同步；未实现的诊断能力继续明确登记为缺口，而不是用静态按钮占位。
