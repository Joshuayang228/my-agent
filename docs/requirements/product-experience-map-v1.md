# 产品体验总图与用户旅程 v1 施工合同

> 状态：进行中
> 生命周期：产品体验总图与主用户旅程对齐阶段；先指导 Playground 候选施工，未取得逐页验收前不得直接回流正式 UI。
> 建立日期：2026-08-30
> 统一称呼：施工合同

## 1. 需求背景（Why）

基础组件和局部页面候选已经基本具备，但继续按“看到一个页面就补一个页面”的方式施工，容易产生三个问题：入口不断增加、页面各自完整却彼此断裂、伙伴的长期关系价值无法被用户感知。

本合同把产品体验从“页面集合”提升为“用户旅程系统”。先明确 My Agent 的核心价值闭环、正式产品入口职责、场景出现条件和跨页面上下文不变量，再按主旅程逐段在 Playground 中建立候选并验收。

本阶段的核心判断不是“每个页面有什么控件”，而是：

```text
用户为什么进入 → 在哪里获得价值 → 为什么愿意回来 → 下一步自然去哪里
```

本合同是产品体验总合同；`product-experience-journeys-v1.md` 是其中 Chat 主旅程的执行子合同，后续人物世界、记忆 / 设置、工作区和状态矩阵应按本合同拆分施工。

## 2. 产品体验北极星（What）

### 2.1 一句话定位

My Agent 是一个**有稳定人格、会记住用户、拥有连续生活世界，并能陪用户完成事情的数字伙伴**。

### 2.2 核心价值闭环

```text
建立关系
  ↓
自然聊天与理解用户
  ↓
记住重要的事
  ↓
伙伴拥有可感知的生活连续性
  ↓
用户回来查看、继续聊天或一起做事
  ↓
关系与实际帮助同时变深
```

### 2.3 三类价值

| 价值 | 用户感受 | 主要承载面 |
|------|----------|------------|
| 陪伴与关系 | “这是同一个伙伴，不是每次都重新认识我” | Chat、记忆、人物世界 |
| 生活连续性 | “它有自己的生活，但不会抢我的注意力” | 朋友圈、衣柜、文化角、家居、通讯录、足迹 |
| 实际帮助 | “它能和我一起把事情做完” | Chat、任务卡、工作区 |

三类价值必须互相支撑：朋友圈不能脱离人格，记忆不能脱离关系，工作区不能脱离 Chat 中用户正在做的事。

## 3. 产品信息架构（How）

### 3.1 正式产品入口

正式产品不把每个能力都做成侧栏一级入口，采用“少量长期目的地 + 场景内出现”的结构：

```text
Primary Sidebar
├─ Chat                  # 默认主入口：聊天、陪伴、发起任务
├─ 人物世界              # 当前主角的生活与关系截面
│  ├─ 朋友圈
│  ├─ 衣柜
│  ├─ 文化角
│  ├─ 家居
│  ├─ 通讯录
│  └─ 足迹
└─ 设置                  # 管理伙伴、角色、记忆、模型、工具与开发者能力
   ├─ 伙伴与角色 / 角色架
   ├─ 记忆
   ├─ 模型与连接
   ├─ 工具与 Skills
   ├─ 外观与行为
   └─ Debug / 开发者

Contextual Surface
└─ 工作区                # 只有任务需要文件、预览、审阅或终端时从 Chat 出现
```

规则：

- `Chat` 是唯一默认落点，也是所有实际行动的主锚点。
- `人物世界` 是一个统一生活面，不把人物世界六个生活面拆成多个一级产品入口。
- `记忆` 属于设置管理，但可以从人物世界或 Chat 的明确上下文进入。
- `工作区` 是任务上下文，不是常驻第二主界面。
- `Debug` 是开发者诊断入口，不进入普通用户的主旅程。
- Playground 可以把这些面拆开验收，但不能据此推导正式产品增加同等数量的一级入口。

### 3.2 五个产品体验面的职责

| 体验面 | 只回答一个主问题 | 不负责什么 |
|--------|------------------|------------|
| Chat | 我现在和伙伴聊什么、做什么？ | 不承载完整设置、诊断目录或常驻工作台 |
| 人物世界 | 这个伙伴最近怎样生活、和谁有关系？ | 不变成事件日志或功能后台 |
| 记忆 | 伙伴记住了什么，这些记忆如何影响关系？ | 不要求用户频繁手工维护全部记忆 |
| 设置 | 我可以控制伙伴的哪些行为与连接？ | 不承载日常聊天和生活动态浏览 |
| 工作区 | 这次任务如何被完成、查看和交付？ | 不脱离 Chat 独立经营一套任务产品 |

“业务状态”不作为正式用户目的地，而是横跨以上体验面的状态验证集合：空态、错误、权限、加载、任务中等都必须回到真实上下文中验收。

## 4. 用户旅程总图

### 4.1 首次使用旅程

```text
打开应用
  ↓
看到当前伙伴与简短身份
  ↓
无需先理解复杂设置
  ↓
发送第一句话 / 点击开始建议
  ↓
获得一次有回应的互动
  ↓
进入正在聊天状态
```

首次使用原则：

- 首屏只解释“我是谁”和“现在可以做什么”。
- 不在空态放换主角、复杂规则、开发信息或完整能力清单。
- 如果模型尚未配置，使用清晰的最短路径进入设置，完成后回到原来的 Chat 上下文。
- 第一轮价值优先于展示功能数量。

### 4.2 日常陪伴旅程

```text
打开应用
  ↓
回到上次的伙伴与会话
  ↓
继续聊天
  ├─ 直接聊今天的事
  ├─ 看到伙伴提及生活动态 → 进入朋友圈
  ├─ 想了解关系连续性 → 查看记忆
  └─ 有事情要完成 → 进入任务工作流
  ↓
回到 Chat，继续关系和行动
```

### 4.3 人物世界旅程

```text
Chat
  ↓
人物世界
  ↓
朋友圈：看近期生活切片
  ├─ 查看图片 / 地点 / 评论等内容
  ├─ 进入衣柜 / 文化角 / 家居：看角色的外在、文化与居所
  ├─ 进入通讯录：看关系与召唤对象
  └─ 进入足迹：看旅行、地点与移动记忆
  ↓
回到 Chat 或进入记忆
```

朋友圈必须是人格生活事件的派生截面，不是独立内容社区；用户看到的图文、地点和互动应服务于“更了解这个伙伴”。

### 4.4 记忆与设置旅程

```text
人物世界 / Chat 明确入口
  ↓
记忆
  ↓
查看、理解或修正重要记忆
  ↓
设置
  ├─ 伙伴与角色 / 角色架
  ├─ 模型与连接
  ├─ 工具与 Skills
  └─ 外观与行为
  ↓
回到 Chat
```

记忆默认是关系的可见证据，不是要求用户管理的数据库；设置才承载明确的控制和配置动作。

### 4.5 任务工作旅程

```text
Chat 中识别到需要完成的任务
  ↓
伙伴说明正在处理什么
  ↓
仅在需要时打开工作区
  ├─ 文件
  ├─ 预览
  ├─ 审阅
  └─ 终端
  ↓
任务进行中 / 等待确认 / 完成 / 失败
  ↓
结果、下一步或失败原因回到 Chat
```

工作区必须有明确的进入原因和退出结果，不能只是把一整套开发工具永久摆在聊天旁边。

### 4.6 角色切换旅程

```text
设置 → 角色架 → 选择主角
  ↓
新的 Chat 身份
  ↓
人物世界六个生活面同步
```

对话进行中不允许换主角；角色切换不是 Chat 空态操作，而是设置中的显式管理动作。

## 5. 跨页面不变量

以下规则必须在 Playground 和正式 UI 中保持一致：

1. **当前主角唯一**：Chat、朋友圈、衣柜、文化角、家居、通讯录、足迹和角色相关设置不能出现不同主角。
2. **上下文可回返**：从 Chat 进入人物世界、记忆、设置或工作区后，必须能明确回到原上下文。
3. **工作区按需出现**：没有任务理由时不常驻；任务结束后结果回到 Chat。
4. **生活面不日志化**：朋友圈展示生活意义，不直接暴露内部事件表、状态标签或实现术语。
5. **记忆不打扰**：记忆只有在用户需要理解、修正或管理关系时出现，不能以空态说明条打断主流程。
6. **开发能力分层**：Debug、Skills、Provider 细节和工具诊断不进入默认用户旅程。
7. **隔离实验不污染生产**：Playground fixture、实验开关、来源路径和演示数据不进入正式 UI 或真实数据链路。
8. **失败可恢复**：模型、工具、权限和任务错误都必须给出下一步，并回到可继续的上下文。

## 6. 可见性分层

| 层级 | 始终可见 | 场景出现 | 开发者可见 |
|------|----------|----------|------------|
| 关系 | 当前伙伴身份、当前会话 | 人物世界入口、记忆引用 | Prompt / 资产证据 |
| 生活 | 人物世界入口 | 朋友圈、衣柜、文化角、家居、通讯录、足迹 | 世界态与事件诊断 |
| 行动 | Chat 输入与会话 | 任务卡、工作区 | 工具调用与 Trace |
| 管理 | 设置入口 | 角色架、记忆编辑、模型配置 | Provider 路由、Skills、Debug |

任何新增入口都必须先回答它属于哪一层，不能因为已有一个组件就增加一个长期导航位。

## 7. 技术方案与施工边界

### 7.1 Playground 施工方式

- 继续使用正式组件和 CSS token 组合页面候选，不复制另一套生产皮肤。
- Playground 只使用隔离 fixture；不读取或写入真实会话、角色、记忆、设置、模型和生活世界。
- 每个产品体验由 `src/shared/product-experience-registry.ts` 声明真实来源和 Foundation 依赖。
- 产品体验页面按本合同的旅程和状态组织，基础组件只在 Foundation 工作域验收。
- 重要交互必须有 Renderer E2E；视觉需覆盖浅色 / 深色、标准宽度 / 窄宽和关键溢出。

### 7.2 正式 UI 回流边界

在用户逐页确认 Playground 候选前：

- 不改变正式 Chat、人物世界、设置、会话、LLM、IPC 或生产数据行为。
- 不把 Playground 来源路径、实验标签、调试滑杆、隔离图片或 fixture 文案带入产品。
- 不因为 Playground 有某个 Tab 就自动增加正式一级导航。

获得明确回流许可后，只选择性同步已经验收的视觉 token、真实交互和页面组合，并更新对应模块卡、质量门禁和变更记录。

## 8. 影响范围评估

- **产品**：从单页组件验收转为按用户旅程验收；入口数量、上下文返路和场景出现条件需要统一。
- **技术**：不新增主进程接口；后续 Playground 页面状态优先在 Renderer 内隔离管理。
- **测试**：需要新增跨页面旅程 E2E，而不是只测页面是否渲染；正常态与关键边缘态必须同时验证。
- **文档**：本合同作为总图；`product-experience-journeys-v1.md`、`playground-navigation-world-polish-v1.md` 作为具体施工子合同；模块卡记录完工后的稳定事实。
- **风险**：入口收敛可能让开发者觉得能力隐藏；通过设置分层、场景入口和全局 Debug 保留可达性。
- **非目标**：本合同不决定完整视觉风格、不定义真实 LLM 文案、不实现社交网络、不实现后台多主角养成。

## 9. 实施步骤

1. **总图对齐**：确认本合同中的北极星、正式 IA、五个体验面和六条主旅程。
2. **Chat 主旅程**：补齐首次进入、正在聊天、任务处理、失败恢复和回到对话。
3. **人物世界**：完成朋友圈、衣柜、文化角、家居、通讯录、足迹的角色连续性与内容层级。
4. **记忆 / 设置**：确定设置分组、记忆入口、角色架、模型和 Skills 的渐进披露。
5. **工作区**：明确任务出现条件、工作区生命周期、结果回流和失败恢复。
6. **状态矩阵**：把空态、加载、错误、权限、禁用和窄宽场景放回真实旅程。
7. **跨旅程验收**：从首次进入走到长期陪伴、任务完成、角色切换和错误恢复。
8. **Playground 收口**：删除重复入口、无意义说明和仅为展示而存在的结构。
9. **正式回流**：逐页取得确认后选择性回流，不一次性大面积改生产 UI。

每一步都必须有：施工前说明、可交互候选、截图 / E2E 证据、文档同步和用户验收结论。

## 10. 风险与权衡

- **少入口 vs 可发现性**：正式侧栏只保留长期目的地，能力通过场景入口和设置分层暴露，避免导航膨胀。
- **伙伴自主生活 vs 用户打扰**：生活世界可持续派生，但默认不通过强提示打断 Chat；需要时由用户主动进入或由上下文自然引导。
- **关系管理 vs 用户负担**：记忆默认自动工作，只有理解、修正和敏感事项才要求用户介入。
- **任务效率 vs 产品气质**：工作区保留专业能力，但只在任务需要时出现，并始终由 Chat 解释上下文。
- **Playground 速度 vs 生产安全**：候选可以快速实验，正式 UI 必须经过明确回流许可证和真实数据边界审计。

## 11. Phase E0 / E1 验收标准

### 总图验收

- 能用一张图解释首次进入、日常陪伴、人物世界、记忆 / 设置、任务工作、角色切换六条主旅程。
- 能明确说明 Chat、人物世界、记忆、设置、工作区各自职责，以及业务状态为何不是正式一级目的地。
- 能明确区分正式产品 IA、Playground 展示 IA 和 Debug IA。

### 旅程验收

- 首次进入不被换主角、Debug、复杂设置或空态说明打断。
- Chat → 人物世界 → 朋友圈 / 衣柜 / 文化角 / 家居 / 通讯录 / 足迹 → Chat 可回返。
- Chat / 人物世界 → 记忆 → 设置 → Chat 可回返。
- Chat → 任务 → 工作区 → 结果 / 失败 → Chat 可回返。
- 设置 → 角色架 → 切换主角后，所有角色相关体验保持一致。
- 模型未配置、权限拒绝、任务失败和无内容空态都有下一步，不形成死路。

### 边界验收

- Playground 不读取或写入真实生产数据；正式 UI 默认行为不因候选施工改变。
- Foundation 与 Experience 依赖从注册表派生，不在页面内复制第二份事实。
- 所有关键旅程覆盖标准宽度、窄宽、浅色 / 深色和键盘可达性。

## 12. 当前开工顺序

本合同确认后，立即进入第 1 个执行子阶段：**Chat 主旅程施工**。

先不同时改人物世界、记忆和设置；先把 Chat 作为主锚点做成一条从“认识伙伴”到“完成事情并回到对话”的完整路径，再逐步接入其他体验面。
