# 足迹旅行记录第一版施工合同

> 状态：进行中，产品边界已确认，方案细节待确认。
> 生命周期：施工完成并同步稳定事实后冻结。
> 2026-10-07：产品边界已由用户确认；数据与交互细节待确认。当前只归档方案，不表示已经实现，也不授权正式回流。

## 1. 背景与目标

足迹回答「她有哪些旅行经历」，不是每日排班、定位历史、附近地点收藏或第二个朋友圈。按地点逐条展示容易碎片化，第一版只展示旅行，一段旅行一条记录。

人物世界保持六个 Tab，不新增日常 Tab。完整每日计划与执行记录属于底层生活机制和 Debug；设置只管理机制配置。此合同不顺带开发日程 Debug 页面。

Alice 参考：`_reference/framework-harness/repos/alice-source/main-chunks/query-B_tFgAOJ.js` 的 `alice_trips` 保存出发地、目的地、起止日期与状态，`day_scripts.trip_id` 关联活动；`alice-source/_extract/index-ppRSWnkN.js` 的 `/debug` 展示日记、每日剧本与位置诊断。参考其旅行容器与活动关联，不把诊断直接搬进产品，不声称 Alice 已有本合同的旅行相册 UI。

## 2. 已确认范围

- 一段旅行一条；明确的一日游、周末出游也算，不以跨城市为硬条件。
- 普通通勤、买咖啡和散步不进入足迹；底层活动记录仍保留。
- 首页展示已经出发的旅行，含进行中与已结束；未出发及出发前取消不算足迹。
- 景点、餐厅、停留点与经历放在旅行详情，不拆成同级首页卡片。
- 无旅行保持真实空态，不生成无来源的经历填充页面。
- 不做地图、定位权限、路线、里程、统计卡或「地点 / 想去」视图。

## 3. 信息与交互方案

首页按实际出发时间倒序，进行中可优先。卡片展示封面、名称、目的地、日期范围；进行中使用轻量状态标签，已结束不重复堆叠状态。入库时间不冒充出发时间。

详情顺序：标题、目的地与日期、封面、旅行故事、按实际发生时间排列的停留经历、相关照片。单日不重复日期区间，进行中用「至今」，预计返回时间不能冒充实际结束时间。尚未发生的停留不展示为历史。

图片槽位尺寸稳定，预览共用 Foundation ImageViewer。无图用简洁占位，不使用语义错误图片；生成中 / 失败保持同一槽位，打开页面不触发生图。真实生成配图不是现实到访证据。

列表与详情读取同一旅行记录，返回恢复滚动和触发项焦点；长文在详情内部滚动。窄屏标题、日期与地名不溢出；hover 显隐动作保留尺寸。普通界面不新增未经确认的 CRUD 表单；Agent 维护接口需要角色归属、校验、审计与事件来源，用户通过对话表达修改意图。

## 4. 逻辑 Schema 与字段字典（待确认）

本表是设计提案，不是已经实现的类型或 SQL。落库前对照人物世界总合同和现有事件 / 资产模型决定映射，禁止 Renderer 存第二份事实。

| 字段 | 类型 / 值 | 含义与约束 |
|---|---|---|
| `id` / `roleId` | string | 稳定旅行 id 与所属主角，读写及媒体按角色隔离 |
| `title` | string | 旅行名称，与目的地分离 |
| `origin` | string 或 null | 已知出发地，未知不编造 |
| `destinations` | 地点引用数组 | 有序目的地，多城市仍是一段旅行 |
| `status` | planned / active / completed / cancelled | 计划 / 进行中 / 结束 / 取消；状态本身不能证明出发 |
| `plannedStartDate` / `plannedEndDate` | YYYY-MM-DD 或 null | 预计日期，只供计划与诊断 |
| `startedAt` / `endedAt` | 时间戳或 null | 实际开始 / 结束，首页要求实际开始有事件证据 |
| `timeZone` | IANA zone | 日期展示依据，不随查看设备时区漂移 |
| `summary` / `story` | string | 摘要与详情故事，不复制原始剧本 |
| `coverImageId` / `imageIds` | string 或 null / string[] | 受控媒体引用，有序、去重、校验角色归属 |
| `stops` | 停留数组 | 每项有 id、地点引用、实际时间、摘要、eventIds、imageIds；同地可重复到访 |
| `eventIds` | string[] | 关联实际生活事件，事件仍是事实来源 |
| `source` | role-pack / agent / user-request | 内容来源；用户意图不自动成为已发生事实 |
| `createdAt` / `updatedAt` / `revision` | 时间戳 / 整数 | 审计与并发版本，不作为旅行日期 |

未出发取消不展示；已经出发后取消剩余计划，保留已发生经历并结束旅行，原因留诊断。不凭同名城市自动归并迟到事件，应使用明确旅行关联与实际时间。

数据流：规划 → 实际事件发布 → 更新旅行状态与经历投影 → 足迹读取 → 明确触发媒体生成 / 绑定。朋友圈可关联同一事件，但分享文案与旅行故事独立；删除朋友圈不能顺带删除旅行事实。

## 5. 实施步骤与授权

1. 确认合同细节与存储映射方向；本轮不改数据库。
2. P0：Playground 隔离 fixture 与候选组合，复用 Foundation；不改正式组件默认布局或正式数据筛选。
3. 用户实际查看可交互候选并明确允许回流；「继续」不替代正式回流许可。
4. P1：打通存储、事件投影、Agent 操作、生图与读取；IPC 四处同步，正式页与故事格同轮更新。
5. 完成真实测试和文档收工后，把稳定事实吸入模块卡 / 架构 / 质量文档，再冻结合同。

P0 是独立可验证的设计实验，不冒充生产能力；P1 必须完整打通真实链条，不交付假接口或无行为按钮。

## 6. 样张与验收

- 一日游、周末旅行、多城市旅行，同级展示完整旅程。
- 进行中、已结束、空态；未出发和出发前取消不展示。
- 无图、生成中、失败、多图、长标题 / 地名 / 故事，图片与动作固定占位。
- 多停留点、同地重复停留、列表详情一致、返回位置与焦点恢复。
- 深浅主题、宽窄视口、键盘操作、图片预览与长文局部滚动。
- Unit 验证筛选 / 排序 / 日期 / 关联；E2E 验证完整流程及失败路径。
- P0 无真实配置 / 会话 / 资产写入；P1 补 Electron 角色隔离、持久化、生图失败恢复与媒体备份证据。

## 7. 影响与风险

预计涉及 Playground、共享呈现、生活事件 / 资产服务、共享类型、IPC、媒体与测试；正式施工前认领文件与接口。本轮仅写合同及文档导航，不改产品代码。

原有常去 / 想去地点不得自动伪装成旅行。开发阶段无需兼容旧数据，但删除必须说明对象和影响，不能清空无关世界数据。旅行识别与归组需要测试，不能只靠 Prompt；图片生成不证明事件发生。完整生活记录的 Debug 展示另记待办，不在本次顺带实现。
