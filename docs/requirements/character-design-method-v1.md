# 通用人物设计与连续性承接施工合同 v1

> 状态：进行中
> 生命周期：人物体系方法落地前的施工合同；稳定事实在完成验收后回流伙伴模块卡与人物制作 Skill。
> 日期：2026-10-31

## 1. 需求背景（Why）

现有人物共创已经能够整理身份、世界、关系、外观、行为和材料，但人物仍主要以 Role Pack 文件集合存在，缺少一套统一的人物设计方法。这样容易出现三类问题：人物只有形容词没有选择机制；朋友只有名册没有双向关系；已有作品角色像刚生成出来，无法承接既有经历。

本合同把舞台剧 / 叙事设计中的人物驱动力、冲突、选择、关系和场景方法，与现有 Role Pack、Prompt 四层组合和世界观套装结合，形成原创人物与既有角色都能使用的通用方案。

## 2. 功能目标（What）

### 2.1 人物设计方法

每个人物必须能够描述：

- 世界位置与戏剧功能；
- 稳定身份与不可违背边界；
- 表层欲望、深层需要、恐惧、价值观和核心矛盾；
- 触发场景、默认反应、例外、事后表现；
- 关系方向、互相需要、摩擦、修复和成长信号；
- 住所、物品、日常节奏和活动；
- 首次冷启、自我介绍和代表性名言；
- 可成长状态、设定来源和确认状态。

### 2.2 既有角色承接

人物类型必须显式区分：

- `original`：原创人物；
- `canon`：已有作品人物，承接公开或用户提供的既有经历；
- `adapted`：基于已有角色但经过明确改编的人物。

既有角色必须分离三条连续性：

1. `canon`：人物进入 My Agent 前已经发生的经历；
2. `current`：人物当前所在世界、地点、关系和状态；
3. `interaction`：人物与用户共同发生的新事件。

三类内容必须保留来源和状态，不能混成一段背景简介。

### 2.3 首次冷启

每个人物必须有独立的首次接触场景资产。首次冷启包含：自我介绍、代表性名言或宣言、第一句后的行动方式、初始关系距离和重复策略。

路飞的默认样本为：

> “我是蒙奇·D·路飞！我要成为海贼王的男人！”

该场景只在首次正式建立关系时触发；普通新聊天不重复播放，除非人物关系被重新建立或用户明确要求重新介绍。

## 3. 技术方案（How）

### 3.1 规范文件

新增 `.agents/skills/character-system-builder/references/character-design-method.md`，作为通用人物设计方法的唯一参考。该文件只描述字段语义、写作方法、状态和验收，不复制生产 schema 或完整人物正文。

同步更新 `.agents/skills/character-system-builder/SKILL.md`，将人物设计方法接入启动、材料采集、关系设计、首次冷启、连续性承接和验收流程。

### 3.2 草稿与 Role Pack 结构

在现有 `CharacterDraft` 基础上增加结构化分区：

```text
dramaturgy       世界位置、戏剧功能、欲望、需要、恐惧、矛盾
decisionRules    触发场景、默认反应、例外和事后表现
continuity       canon / current / interaction 三条经历线
firstContact     首次冷启、自我介绍、名言、重复策略
evidence         来源、状态、用户决定和待确认项
```

既有 Role Pack 对应落点：

- `protected.md`：稳定身份、核心价值和不可违背边界；
- `profile.json`：结构化身份、驱动力、外观和表达；
- `relations.json`：双向关系、摩擦、修复和成长信号；
- `world.default.json`：住所、物品、地点和日常活动；
- `timeline/canon.json`：已有作品或既有经历；
- `timeline/current.json`：当前状态；
- `timeline/interaction.json`：用户共同经历；
- `scenes/first-contact.md`：首次冷启；
- `scenes/*.md`：普通、冲突、修复和里程碑场景；
- `behaviors/*.md`：功能人物适配，不重写平台协议。

### 3.3 Prompt 装配

继续使用既有顺序：

```text
平台约束 → 功能协议 → 人物适配 → 运行时资料 → 输出协议
```

新增的人物设计字段只进入“人物适配”或“运行时资料”。既有经历按当前场景检索后注入，不能把完整时间线每次都塞入主 Prompt。首次冷启使用独立场景配方，不由普通主对话 Prompt 猜测。

### 3.4 Debug 展示

Debug 的人物资产目录新增以下可读标签：

- 人物类型：原创 / 既有角色 / 改编角色；
- 连续性：既有经历 / 当前状态 / 用户共同经历；
- 场景：首次冷启 / 普通日常 / 冲突 / 修复 / 里程碑；
- 证据状态：已确认 / 有来源 / 创作提案 / 可变化 / 待决定。

未归类资产仍进入“其他定义 / 待归类”，不能因为新增字段而丢失目录项。

## 4. 实施步骤与验收

1. 写入人物设计方法参考，列出字段、示例、反例和材料采集顺序。
2. 更新开发 Skill，使其能按人物类型选择原创、既有角色或改编流程。
3. 扩展运行时草稿结构，保存首次冷启、连续性和证据状态。
4. 扩展 Role Pack loader / 校验，缺失可选文件显示缺失，不虚构内容。
5. 为路飞补齐首次冷启、既有经历承接和三条连续性样本；原作长段落不进入生产资产。
6. 将人物资产聚合到 Debug，验证来源、版本、指纹和实际 Prompt 关联。
7. 补充单元测试、资产门禁、人物草稿测试和首次冷启 / 连续性边界测试。
8. 运行 `npm run assets:check`、`npx tsc --noEmit`、`npm run test`、`npx vite build`、`npm run docs:validate`。

验收重点：首次冷启只触发一次；既有经历不会被误写成用户记忆；当前状态与用户共同经历分离；人物适配不能覆盖平台约束；关系必须支持方向性；缺失材料不能由 loader 脑补。

## 5. 影响范围与风险

涉及人物制作 Skill、人物草稿类型与存储、Role Pack loader、Prompt 编译、Debug 资产聚合、路飞 Role Pack、测试和伙伴模块文档。现有聊天协议、权限、工具安全和数据库历史事实不改。

既有作品角色存在资料不完整和来源混淆风险，因此所有非用户确认内容必须标记状态；既有经历只作为人物可用背景，不能自动变成当前事实。首次冷启名言只保存短句和来源说明，不复制原作长文本。

## 6. 明确不做

本合同不实现多主角同时后台生活、不自动抓取完整作品、不把整部作品正文写入人物资产、不允许人物 Prompt 覆盖平台权限、不把 Debug 目录变成编辑器。人物编辑和发布仍遵守现有用户草稿、审阅和发布边界。
