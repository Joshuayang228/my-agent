## 1. 需求背景（Why）

人物世界的 W0–W6 主线已经落地：稳定角色、单活跃角色、LifeEngine、事件、朋友圈、生活资产、通讯录和六个正式生活面都已有真实边界。但当前系统仍缺少一层统一模型来回答：

```text
这个人物现在是谁？
她当前处于什么状态？
她拥有和经历过什么？
这些事实如何变化？
用户如何从一条朋友圈理解一段完整生活？
```

如果继续只在六个页面上补内容，会出现三个风险：

1. 当前状态、长期资产和历史事件被混进同一个 JSON 或展示卡片。
2. 朋友圈、衣柜、家居、足迹和通讯录各自拥有局部事实，无法形成同一个人物世界。
3. 用户看到的是零散动态，不是可以回到 Chat 继续相处的生活连续性。

Alice 的源码和方法论提供了可借鉴的分层：稳定主人设、可变人格、角色当前状态、居住状态、日剧本、世界事实、事实变更历史和朋友圈投影。但 My Agent 不直接复制 Alice 的自动虚构生活，而是在现有 Role Pack、`world_json`、`companion_assets`、`companion_events` 和 `companion_moments` 之上建立自己的边界。

## 2. 产品目标（What）

### 2.1 核心目标

建立一套可解释、可回放、可扩展的人物世界模型，并补齐用户可见的“生活切片”体验：

```text
朋友圈动态
  ↓
生活切片 / 事件详情
  ├─ 发生了什么
  ├─ 时间与地点
  ├─ 涉及哪些生活资产或关系
  ├─ 是否留下后续相处线索
  └─ 回到 Chat 继续聊
```

### 2.2 数据分层目标

| 层 | 职责 | 现有 / 计划落点 |
|------|------|------|
| 稳定身份 | 姓名、身份、核心背景、行为边界、表达基线 | Role Pack、`profile.json` |
| 可演化人格 | 长期相处形成的偏好、工作方式和关系阶段 | `companion_mutable` |
| 默认世界 | 角色被确认的住所、地点、资产和生活锚点 | `world.default.json` |
| 当前世界状态 | 当前地点、活动、短期心情、精力、社交状态 | `world_json` / `companion_role_state` |
| 长期生活资产 | 衣物、文化内容、家居、地点、图片等可持续实体 | `companion_assets` |
| 生活事件 | 计划、发生、取消和完成的生活变化 | `companion_day_scripts` / `companion_events` |
| 事件关联 | 事件涉及的资产、地点、角色、图片和 Moment | `companion_event_links`；按 `role_id + event_id` 隔离并可回放 |
| 用户可见投影 | 朋友圈、Catch-up、presence 和生活切片 | `companion_moments` / 运行时投影 |

### 2.3 六个生活面的职责

| 生活面 | 主要问题 | 数据职责 |
|------|------|------|
| 朋友圈 | 最近发生了什么？ | 事件的近期可见投影，不拥有独立事实 |
| 衣柜 | 她如何呈现自己？ | 衣物与穿着资产；具体穿着行为由事件引用 |
| 文化角 | 她被什么打动？ | 书、音乐、电影、摄影和笔记等长期文化资产 |
| 家居 | 她在哪里生活？ | 住所、房间和生活物件等空间资产 |
| 通讯录 | 她和谁有联系？ | Role Pack 关系资料与运行时关系状态的用户视图 |
| 足迹 | 她去过或想去哪里？ | 地点资产与事件产生的访问 / 移动记录 |

### 2.4 Alice 参考边界

第一版人物世界的六个主要 UI 已经确定，本合同不因参考 Alice 而重新拆分、合并或删除这六个入口。Alice 只作为视觉与交互参考来源：

- **信息展示**：参考图片、动态内容、生活信息的层级、节奏、密度和展示方式；不复制 Alice 的产品语义。
- **辅助元素**：评估是否需要空间感、示意图、角色生活场景或生图；是否采用由我方人物世界目标和真实数据边界决定。
- **具体模块**：对衣柜、家居、足迹等逐面研究 Alice 是否有生图、空间化展示、分类和资产排版，再转译为我方组件与数据结构。
- **文化角**：即使 Alice 没有对应的生活面，也必须保留文化角；文化角按我方“文化、兴趣与表达”目标独立设计，不因参考项目缺少对应模块而删除或降级。
- **参考项目缺口**：Alice 没有覆盖的模块标记为“我方自有设计”，不能为了保持参考一致而制造空白、合并入口或删除已有能力。

### 2.5 当前执行基线

后续施工统一按以下基线推进，避免在局部修补中丢失产品上下文：

1. 六个生活面是已确定的产品边界：朋友圈、衣柜、文化角、家居、通讯录、足迹必须全部保留。
2. Alice 只提供图片 / 生图、信息展示层级、内容密度、空间感和模块排版的参考；产品语义、数据边界和文化角设计以 My Agent 为准。
3. Playground 是候选验收场，不是生产数据浏览器。候选必须使用 Foundation 组件和隔离 fixture；未取得明确验收许可前，不改正式人物世界的默认 UI 或生产数据链。
4. UI 与数据链并行推进：先冻结最小数据语义和用户旅程，再做候选；候选验收后冻结数据库 / IPC 契约，补真实后端，最后回流正式页面。
5. 任何阶段都要保留完整的默认态、长内容、图片 / 生图结果、空态、错误态和编辑 / 返回路径；不能只完成看起来能展示的单一路径。

6. 事件是事实源，Moment 是用户可见投影，资产是长期生活实体；关联不能只藏在长文本中，必须能查询、重建、备份和恢复。
7. 稳定身份 / 默认世界 / 关系资料、可演化人格、当前短期状态、生活资产、已发生事件和朋友圈投影必须分层；Prompt 只消费薄切片，不能反向成为人物世界真相。
8. 对话和人物世界的图片都走真实生图、受控媒体读取、资产归属和备份恢复链；本合同不扩展提示词策略，也不在打开人物世界时自动触发高成本生图。
9. 正式页面不直接展示表名、`target_type`、tick、Catch-up 等内部实现术语；用户看到的是生活叙事、关联资产和关系线索。
10. RAG、MCP OAuth、完整 PTY、跨设备同步和旧数据兼容迁移保持后置，不得插入本轮人物世界施工。

### 2.6 目标模式持久化补充（2026-09-30）

为避免长对话或目标模式切换后丢失上下文，以下内容是本合同的硬性完成定义，优先于局部页面印象：

1. **产品边界**：第一版只围绕六个已确定生活面推进：朋友圈、衣柜、文化角、家居、通讯录、足迹。六面都必须有清晰的用户问题、数据来源、默认态、空态、错误态和返回路径；不能因为 Alice 没有某一面而删除、合并或降级，尤其不能删除文化角。
2. **参考边界**：Alice 只用于研究图片 / 生图、空间感、信息层级、分类和排版。最终文案、数据语义、事实来源、生活连续性和模块取舍由 My Agent 决定；禁止把 Alice 的虚构人物事实、自动生活机制或内部表结构直接带入生产。
3. **施工顺序**：先在 Playground 用 Foundation 组件和隔离 fixture 建立候选并验收；再冻结数据库 / IPC / 事件投影契约，补齐真实链路；最后把已验收候选回流正式人物世界。正式页面不能反向发明一套脱离基础组件和真实数据的孤儿 UI。
4. **数据完成定义**：必须区分稳定身份、可演化人格、当前短期状态、长期生活资产、已发生事件、事件关联和用户可见投影；事件是事实源，Moment / 朋友圈是投影，关联必须可查询、可回放、可备份恢复并按角色隔离。
5. **生图完成定义**：对话和人物世界中需要视觉资产的入口接入真实生图、受控媒体读取、资产归属、生成中 / 成功 / 失败或空态及备份恢复；本轮先接通能力，不把提示词策略和自动高成本触发扩展为本合同目标。
6. **体验完成定义**：短内容、长内容、图片、生图结果、空态、错误态、编辑态、展开 / 收起、hover 和返回路径都必须可验收；长内容只能在局部容器内滚动，不能拖动整个应用布局；hover 或出现操作按钮前后必须保持宽高和布局几何稳定。
7. **回流完成定义**：正式人物世界必须使用经过验收的 Foundation / Playground 组合态；不能只回流颜色或静态样张而遗漏交互、错误路径、真实数据和入口。发现正式页与候选不一致时，先回到候选修正并重新验收，再回流。
8. **收工门禁**：已完成自审、定向回归、全量测试、类型检查、构建、资产、文档和正式入口 / Electron 证据；本合同因此冻结为已完成施工快照。
9. **本轮收工证据**：全量 Unit 185/185、UI E2E 381/381、TypeScript、Vite / Electron build、assets 38/38、docs:validate，以及朋友圈备份恢复 Electron 1/1 均已通过；此前模型输入边框、编程套餐样张计数和人物世界图片卡高度的旧回归契约已按当前产品基线收口。
10. **明确后置项**：RAG、MCP OAuth、完整 PTY、跨设备同步和旧数据兼容迁移继续记录为后置，不得为了制造“全都完成”的假象塞入人物世界本轮；开发阶段允许按已确认策略破坏性重置测试数据。

## 3. 明确不做（Non-goals）

本合同不包含：

- 重做 W0–W6 已完成主线。
- 新增“事件日志”或“世界状态”一级用户入口。
- 直接复制 Alice 的全部自动生活模拟、地点生成和虚构事实机制。
- 没有 Role Pack 或用户确认时自动补写职业、住所、经历、关系和兴趣。
- 本合同内的最终人物 Prompt 文案重写。
- RAG、MCP OAuth、跨设备同步、多账户关系网络。
- 打开人物世界时自动触发高成本生图；生图继续由用户或 Agent 明确触发。
- 让人物情绪或关系阶段阻断用户的正常工具任务。
- 为旧数据增加兼容迁移层；开发期继续遵守已确认的破坏性重置策略。

## 4. Alice 对照与我方取舍

### 4.1 吸收的结构

Alice 的源码快照中明确存在或使用了以下概念：

- `character_state`：角色当前状态。
- `day_scripts`：未来生活计划。
- `world_facts`：角色当前拥有或经历过的世界事实。
- `fact_events`：事实的购买、交付、损坏、修复和退役等变化历史。
- `world_pending_events`：尚未完成的世界变化。
- `moments`：用户近期可见的生活动态。
- 住所与房间场景：作为独立的居住世界，而不是人物简介中的一句话。

这些结构共同保证：

```text
当前状态 ≠ 历史事实 ≠ 朋友圈展示
```

### 4.2 我方差异

My Agent 保留更严格的来源和确认边界：

1. Role Pack 是稳定人物事实的来源，不能由朋友圈反推人物设定。
2. `companion_assets` 是长期生活资产，`companion_events` 是变化事实，`companion_moments` 是投影。
3. 生活内容可以有连续性，但未经确认的生活事实不能因为“看起来合理”而写入生产数据。
4. 用户看到的是生活叙事，不是 Alice 内部的 `character_state`、`world_facts` 或 `fact_events` 表。
5. 事件与资产、地点、关系的关联必须可以解释和回放，不能只依靠不可查询的长文本。

### 4.3 UI 参考与产品主导关系

```text
我方六面产品目标与用户旅程
  ↓ 决定模块是否存在、回答什么问题
Alice 参考
  ↓ 提供图片、空间、信息层级和交互表现的启发
Playground 候选
  ↓ 验收我方版本是否舒适、连贯、可实现
正式人物世界
```

因此，参考 Alice 只能影响“怎么呈现”，不能推翻“我们为什么有这个生活面”。任何模块都必须先通过我方用户问题、数据来源和生活连续性检查，再决定是否吸收参考做法。

## 5. 技术方案（How）

### 5.1 推荐数据流

```text
Role Pack / 用户确认的稳定资料
  ↓
稳定身份与默认世界
  ↓
planned event / 用户行动 / Agent 工具 / LifeEngine tick
  ↓
published event（事件事实）
  ├─ 更新当前世界状态
  ├─ 关联生活资产、地点、关系和图片
  ├─ 投影 Moments
  ├─ 形成 Catch-up
  └─ 供 Chat Prompt 组装消费
```

### 5.2 当前表的职责保持清晰

第一阶段不直接推翻现有表，而是先冻结职责：

```text
profile.json / Role Pack
  = 稳定身份和行为基线

companion_mutable
  = 可演化人格

world_json
  = 当前短期世界快照

companion_assets
  = 长期生活资产

companion_events
  = 计划与已发生事件

companion_moments
  = 近期朋友圈投影
```

Prompt 只能读取各层经过边界处理后的薄切片，不能把整张资产表、事件表或 `world_json` 原文灌入上下文。

### 5.3 数据模型决策与剩余问题

以下问题仍需在施工中明确，但不再阻塞已经批准的生活切片最小链路：

1. `companion_events.scheduled_at` 是否需要与实际发生时间拆开，避免“计划时间”和“事实时间”混义。
2. `companion_events.payload_json` 是否足以表达事件详情，还是需要稳定的事件摘要、来源和可见性字段。
3. `companion_assets.source_event_id` 与统一事件关联表的职责如何长期并存；首版保留旧字段，同时以关联表表达多对多关系。
4. 地点、角色、图片和资产统一使用 `companion_event_links`；若未来某一领域需要额外生命周期，再增加领域字段，不另造一套并行关系表。
5. `world_json` 中哪些字段属于当前状态，哪些字段必须回写事件或资产，避免快照覆盖历史。
6. 通讯录关系是否需要独立的运行时状态表，还是先由 Role Pack 关系与事件投影表达。
7. 资产的 `active / pending / gone` 等生命周期是否需要从 `payload_json` 提升为结构化字段。

第一版已批准并正在施工的统一关联结构：

```text
companion_event_links
  id
  event_id
  role_id
  target_type
  target_id
  relation
  metadata_json
  created_at
```

当前实现约束：关联必须同时匹配 `role_id + event_id`；唯一键为
`(event_id, target_type, target_id, relation)`；事件不存在、角色不匹配或目标归属不明时拒绝写入；`metadata_json` 只保存可解释的补充信息，不用来替代核心外键。

### 5.4 UI 方案边界

生活切片优先作为朋友圈卡片的详情态、内联展开或应用内详情面，而不是新增人物世界一级 Tab。候选必须：

- 使用正式 Foundation 组件和主题 token。
- 先在 Playground 使用隔离 fixture。
- 同时覆盖短事件、长事件、无关联资产、关联多项资产和读取失败。
- 长内容在局部容器内滚动，不拖动整个应用布局。
- 展开 / 收起、hover、编辑和操作槽都保持布局几何稳定。
- 明确回到原朋友圈位置或回到 Chat 的路径。

## 6. 影响范围评估

### 6.1 可能修改

- Playground 人物世界候选与生活切片故事。
- `companion` 领域类型、查询和投影逻辑。
- SQLite schema / migration（仅在模型决策后）。
- IPC 四处契约（仅在新增真实能力后）。
- WorldHub / MomentsPanel 及共享 Foundation 组合。
- 备份恢复、Prompt 薄切片和 Debug 只读证据。
- Unit、Renderer E2E、Electron 验证、质量文档和模块卡。

### 6.2 当前明确不做

本合同当前不做：

- 新增人物世界一级 Tab 或内部事件日志入口。
- 复制 Alice 的自动虚构生活、地点生成或事实推进机制。
- 重写最终人物 Prompt、Role Pack 故事和 RAG 注入策略。
- 自动把打开页面、普通 tick 或浏览行为变成高成本生图请求。
- RAG、MCP OAuth、完整 PTY、跨设备同步和旧数据兼容迁移。

候选验收已经完成后，数据库、IPC、事件发布投影和正式生活切片 UI 属于本合同当前施工范围；不再沿用“候选验收前禁止施工”的过时描述。

### 6.3 风险

| 风险 | 处理方式 |
|------|------|
| 过早增加表导致模型僵化 | 先用候选验证事件详情真正需要的关系 |
| 朋友圈变成后台日志 | 用户视图只展示生活意义，内部状态留在 Debug |
| 当前状态覆盖历史事实 | 明确快照、事件、资产三者写入边界 |
| 自动生活生成编造事实 | Role Pack / 用户确认来源门禁，缺证据保持空态 |
| 关联过多导致详情页拥挤 | 先定义首要叙事，再渐进披露相关资产和关系 |
| UI 回流跳过 Playground | 严格执行 Playground 候选 → 用户验收 → 正式回流 |

## 7. 实施步骤与验收闸门

### P0：研究与设计冻结（已完成，作为持续约束）

1. 对照 Alice 源码、现有表结构、模块卡和事件方法论，完成字段职责矩阵。
2. 明确静态、可演化、当前状态、资产、事件、投影和用户记忆的边界。
3. 形成至少两套事件关联方案的取舍记录。
4. 产出本合同的设计决策补充，并由用户确认后进入 Playground。

验收：每个现有字段能说明“谁写、何时写、是否可回放、谁消费”；不存在两个模块共同拥有同一事实。

### P1：Playground 生活切片候选（主要体验已验收）

1. 使用正式组件建立朋友圈到生活切片的候选。
2. 覆盖单事件、多资产关联、地点和关系、无关联资产、长正文、空态和错误态。
3. 验证返回 Chat、返回原列表位置、窄宽滚动、深浅主题和布局稳定性。

验收：用户能理解“发生了什么”和“为什么与这个伙伴有关”，但看不到内部表名、事件状态或实现术语。

### P2：数据模型与真实链路施工（已完成）

在 P1 验收基础上：

1. 完成 `companion_event_links` 的测试库建表、幂等写入、角色隔离读取和持久化。
2. 在事件发布 / Moment 投影时统一写入资产、卡司和图片关联；地点继续使用事件结构化字段，不从地点文字猜资产。
3. 将事件、Moment、资产和关联一起返回生活切片；事件没有 Moment 时仍可返回事件与关联事实。
4. 按 IPC 四处同步原则接入真实读写，补齐失败转换、备份恢复、删除和孤儿关联语义。
5. 补齐长正文、关联多项资产、无关联、错误 / 重试和跨角色的 Unit / E2E。

验收：删除 Moment 不影响事件；删除事件不会留下孤儿关联；角色切换不会混合数据；从事件可重建用户可见投影。

### P3：正式回流与收工（已完成）

1. 用户确认 Playground 候选后回流正式 UI。
2. 补 Prompt 薄切片、Debug 证据和正式入口 E2E。
3. 按顺序完成自审、测试、类型检查、build、UI / Electron、资产和文档门禁。
4. 把稳定事实吸收到模块卡、Architecture、Quality、Decisions 和 progress，再冻结本合同。

## 8. 必测点

- 当前主角唯一，事件、资产、Moment 和生活切片全部按 `role_id` 隔离。
- planned / published / cancelled 的生命周期和时间边界。
- 事件与资产、地点、关系、图片的关联完整性。
- 朋友圈投影可从事件重建，不反向作为事实源。
- 事件详情长内容局部滚动，不能撑开整个应用。
- 展开、收起、hover、加载、失败和重试前后布局几何稳定。
- 备份恢复不产生孤儿事件、资产或图片引用。
- Prompt 只消费薄切片，不读取 UI 私有状态或整库数据。
- Playground 不读写生产 IPC、会话、设置或人物世界数据。

## 9. 合同确认边界

本合同当前获得的授权覆盖：

- 研究 Alice 与现有实现。
- 完成字段职责和数据流设计。
- 在 Playground 建立并验收生活切片候选。
- 按本合同已批准的最小结构施工 `companion_event_links`、生活切片查询和关联展示。
- 在 P2 真实链路通过后，将已验收候选回流正式人物世界。

以下行为仍需要额外设计确认或新合同：

- 改变六面入口或删除 / 合并文化角。
- 引入新的世界事实来源、自动虚构生活或跨角色共享事实。
- 改变 Prompt 的最终人物语义、RAG 注入策略或 MCP OAuth。
- 引入跨设备同步、多账户关系网络或旧数据兼容迁移。

## 10. 施工节奏与 UI 时机

本合同采用“语义先行、候选并行、正式后置”的节奏，不等待整个后端全部完成后才开始 UI，也不允许先做一套脱离数据的正式页面：

```text
P0：字段职责与数据流盘点
  ↓
P1：Playground 生活切片候选（隔离 fixture）
  ↓ 用户验收体验与信息层级
P2：冻结数据库 / IPC / 投影契约并实现真实链路
  ↓
P3：将已验收候选回流正式人物世界
```

这样安排的原因：

- 如果先完成全部后端，可能把用户并不需要的事件详情字段和关联表做死。
- 如果先做正式 UI，页面会反向发明自己的状态，违反“产品体验从基础与真实数据链生长”的原则。
- Playground 候选可以先验证用户需要看到的叙事层；P0 只需先冻结最小语义，不需要提前冻结所有 schema。
- P2 的数据库设计必须服务于已验收的生活切片，而不是让 UI 迁就内部表结构。

因此，本合同的施工链已完成：P2 真实链路通过后，已验收候选已回流正式人物世界，并按本合同门禁完成收工。后续涉及 RAG、MCP OAuth、完整 PTY、跨设备同步或旧数据兼容的工作必须另行开工，不得回写本冻结快照。

## 11. P0 当前字段职责矩阵（施工起点）

以下矩阵是对现有实现的盘点，不是新增字段授权：

| 当前结构 | 已有字段 / 内容 | 当前写入时机 | 当前消费方 | 结论 |
|------|------|------|------|------|
| `RoleProfile` | 身份、背景、习惯、兴趣、表达基线、外观 | Role Pack 资产加载 | Prompt / Debug / 角色身份 | 稳定身份；不放当前心情或当前位置 |
| `RoleWorldDefaults` | 城市、住所、房间、地点、物品、作息、初始状态 | Role Pack 初始化 | 世界初始化 / 空态 / Prompt | 默认世界；无证据时保持未设定 |
| `companion_mutable` | 可演化人格正文与版本 | 设置保存 / 反思 | Prompt / 反思 | 可演化人格；不能覆盖稳定身份 |
| `companion_role_state.world_json` | home、timezone、situation、mood、energy、socialNeed、currentLocation、currentActivity 等 | 初始化 / published 事件刷新 / 状态更新 | Catch-up / Prompt / 世界状态 | 当前短期快照；不承担历史 |
| `companion_day_scripts` | 日期、主题、时间槽、活动、地点、心情 | 日剧本生成 | LifeEngine / 事件生成 | 计划来源；不是已发生事实 |
| `companion_events` | role、scheduledAt、status、type、payload、dayScriptId | 计划创建 / 到时发布 / 取消 | Moments / 世界状态 / Catch-up | 事件事实；需继续确认计划时间与实际时间边界 |
| `companion_moments` | eventId、publishedAt、text、meta | 已发布事件投影 | 朋友圈 / 互动 / 近期上下文 | 可重建投影；不独立编造生活事实 |
| `companion_assets` | role、kind、name、payload、acquiredAt、sourceEventId | Role Pack 播种 / 用户编辑 / 事件授予 / 生图绑定 | 衣柜 / 文化角 / 家居 / 足迹 / Prompt | 长期生活资产；事件多对多关联仍待确认 |
| roster / relations | Role Pack 关系边与名册摘要 | Role Pack 加载 | 通讯录 / 召唤 / Prompt | 稳定关系资料；运行时关系状态仍待确认 |
| 用户记忆 | 用户身份、偏好、关系记忆 | Chat 后处理 / 用户修正 | Memory / Prompt | 不并入人物世界事实；只通过明确关系入口关联 |

P2 的当前工作是继续补齐每一行的“事实所有者、可回放性、生命周期和失败语义”，完成事件关联表的读写与投影接线；随后用真实链路验证 P1 候选，再进入 P3 正式回流和收工门禁。
