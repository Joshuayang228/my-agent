## 一、第一性原理

**伙伴的可信赖感来自可见性——用户不需要盯着它，但它必须让你知道它在做什么。**

这条原理标出了伙伴型 Agent 和命令式 Agent 的核心差异。

CC（Coding Agent）的后台任务只要最终完成就行。用户发出指令，Agent 去执行，完成后返回结果。过程不透明可以接受，因为用户的信任建立在"交付"而不是"关系"上。

伙伴型 Agent 不同。每一次后台行动——提取了你说的偏好、更新了对你的理解、索引了你分享的文件——都是关系建立的一部分。做了但没有告诉用户，等于没做。用户无法感知"它一直在学习和成长"，伙伴感就只停留在对话框里的措辞，不是真实的行为。

**推论地图**：

```
根认知：伙伴可信赖感来自可见性
    │
    ├─ ① 可见性的最小实现 → 三个关键节点通知（§2）
    │
    ├─ ② 可见性要求幂等 → 通知只能发一次，任务只执行一次（§3）
    │
    ├─ ③ 后台不等于前台 → token 和预算独立计数（§4）
    │
    ├─ ④ 任务的产出归宿 → 任务队列是记忆系统的刷新管道（§5）
    │
    └─ ⑤ 长任务的可见性持续 → 持久化状态，断线可恢复（§6）
```

## 二、可见性的最小实现：三个关键节点

"可见性"不等于"全程直播"。后台任务的每一个细节都推给用户，是骚扰，不是陪伴。

可见性的最小有意义实现是三个关键节点的状态通知：

```
任务开始  → "正在为你做 X"
任务完成  → "我更新了你的偏好：你喜欢简洁的回答"
任务异常  → "无法完成 X，原因是 Y"
```

这三个节点对应用户真正需要感知的信息：
- **开始**：知道它在行动（不是死机）
- **完成**：知道行动的结果（能不能信任它做了什么）
- **异常**：知道出了问题（需不需要介入）

**设计判断**：这不是 Toast 通知。Toast 是临时浮层，用户看了就过去了。任务状态应该是持久的——用户切换会话后回来，能在某个地方看到"上次做了什么"。对应 CC 的 DreamTask "正在为你做 X" pill，是常驻 UI 状态，不是一次性消息。

## 三、幂等性：任务只执行一次，通知只发一次

可见性的前提是可靠性。如果同一个后台任务被触发两次、通知被发送三次，用户看到的是混乱而不是透明。

**什么情况会触发重复执行**：
- 对话完成后自动触发记忆提取，用户在 2 分钟内又发了消息，第二次对话结束后再次触发
- Electron 进程崩溃重启，上次未完成的任务重新入队
- 用户在两个窗口打开同一个会话（如果将来支持多窗口）

**幂等设计的两个层面**：

**任务幂等**：每个任务需要一个唯一标识（`sessionId + taskType + triggerTimestamp` 的哈希，或 UUID），在执行前先检查这个任务是否已经完成。已完成 = 跳过；正在执行 = 等待而不是并发启动；未开始 = 正常执行。

**通知幂等**：每个通知事件标记一个 `notified: boolean` 字段。通知发送后置为 true，任何重发逻辑都先检查这个标志。CC 的任务系统里，`notified` 是防止重复通知的显式字段（`InProcessTeammateTask` 的设计）。

**推论**：幂等性要求任务状态必须持久化，不能只活在内存里。进程重启后，任务状态必须从持久存储（SQLite）恢复，而不是丢失然后重新触发。

## 四、前后台 Token 分离：不让辅助任务污染主对话预算

当前实现里，三类辅助任务的 token 消耗已经统一经过 `chatComplete()`（M3 G1 的成果）——但这些 token 和主对话的 token 被计入同一个统计维度。

**这个问题在伙伴型 Agent 里格外重要**：

如果用户开启了"每日 token 预算 100K"，而后台记忆提取平均每天消耗 20K，那么用户的实际对话预算只有 80K——但用户看到的预算提示无法区分哪部分是真正花在对话上的。后台越活跃（记忆越丰富、学得越快），用户感知到的预算越紧张。这与"越了解你的伙伴越值钱"的产品定位矛盾。

**设计方向**：

```
token 计数维度
├─ 主对话（caller = 'main'）      → 计入用户当前会话的 session 预算
├─ 辅助任务（caller = 'summary'   → 记入全局辅助 token 池，不占 session 预算
│            caller = 'profile'
│            caller = 'title'）
└─ 后台任务（future M11 tasks）   → 同辅助任务
```

M3 已经打了 `caller` 字段，M11 需要把任务的 token 消耗归入独立维度并在 DevPanel 里分项显示。

## 五、任务队列是记忆系统的刷新管道

这是 M11 和其他框架模块关系最重要的一条。

当前的记忆提取是直接嵌在 runtime 的 `enqueuePostTasks()` 里的 fire-and-forget——对话完成后，异步启动 `maybeExtractProfile()` 和 `addToVectorStore()`，没有状态管理，没有失败重试，没有对用户的通知。

从 M11 的视角看，这些任务是记忆系统的"原料到知识"转化管道：

```
用户对话（原料）
    ↓  M11 任务队列
记忆提取（extractProfile）
    ↓
SQLite 记忆条目
    ↓  再次触发向量索引
向量嵌入（addToVectorStore）
    ↓
下次对话的语义召回
```

**管道关系的设计推论**：

- **M11 失败 = 记忆降级**：任务失败不只是"这次没做"，而是"下次对话的记忆质量会下降"。失败必须有重试策略（指数退避，最多 3 次），重试耗尽后的最终失败需要通知用户，而不是静默降级。

- **M11 的产出是 M5 的输入**：记忆系统（M5）的召回质量取决于 M11 的写入质量。如果向量索引任务积压（比如应用离线时大量对话堆积），召回会使用旧的嵌入，用户偏好无法及时更新。M11 需要考虑积压时的优先级策略（最新的任务优先 vs 顺序处理）。

- **feiche 的 StartLinkedAsyncSpan 模式**：后台任务创建 linked span，不影响主 trace 但可追溯。这让可观测性系统能区分"主对话时间"和"后台任务时间"，不会把 5 分钟的向量索引计入某次对话的响应延迟。

## 六、长任务可恢复：持久化状态，断线接着跑

记忆提取和向量索引是短任务（秒级）。但 M11 的设计必须考虑将来更长的后台任务：分析用户的大量历史对话、为新建的 RAG 文档建索引、跨会话的数据整理。

这些任务的特点：
- 执行时间分钟级甚至更长
- 用户可能在中途关闭应用
- Electron 进程可能因为系统更新重启

**可恢复的条件**：

1. **任务状态持久化**：`pending / running / completed / failed / cancelled` 五态，存入 SQLite。进程重启后，`running` 状态的任务被视为中断，根据策略决定是从头开始还是从断点续接。

2. **幂等的子步骤**：长任务如果有"已处理 N/M 条记录"这样的进度，每条处理完就持久化进度。重启后从上次的断点继续，不从头。

3. **断线重连后主动同步**：用户切换到后台，任务继续运行；用户重新打开应用，M11 检查有没有未通知的完成事件，主动推送结果。

CC 的 `InProcessTeammateTask` 里有 `lastReportedToolCount` / `lastReportedTokenCount` 两个字段，作用就是跟踪"上次同步到 UI 的进度"和"当前实际进度"之间的 delta——M11 的进度通知机制可以对照这个设计。

## 七、CC 的任务状态机参考

CC 的 `tasks/` 目录实现了完整的多类型任务状态机，是 M11 设计的最重要参考：

**任务状态**：
```
pending → running ↔ idle → completed / failed / killed
```

**关键设计**：`idle` 是中间态，表示任务存活但当前没在执行（等待工具结果、等待用户输入）。这和 `completed` 的区别很重要——一个长任务可以多次进出 `idle`，每次恢复都回到 `running`。

**InProcessTeammateTask 的进度追踪字段**：

```typescript
progress?: { toolUseCount, tokenCount, recentActivities }
messages?: Message[]    // UI 镜像，上限 50 条
lastReportedToolCount: number
lastReportedTokenCount: number
isIdle: boolean
```

`lastReportedXxx` 字段是"已同步给 UI 的状态"，`progress` 是"实际运行状态"。每次 UI 更新只同步 delta，不重发全量——这是大量频繁后台更新时的性能优化。

**与我们当前实现的 gap**：我们的 `runtime.ts` 里的 `backgroundQueue` 是内存数组，没有状态持久化，没有进度追踪，没有 idle/running 状态，没有对用户的通知机制。M11 需要从这里开始系统性地重建。

## 八、伙伴 vs Coding Agent：任务可见性的根本差异

为什么 CC 的任务系统可以 fire-and-forget 而伙伴不行？

**CC 的用户期望**：
- 我发出一个命令
- Agent 去执行
- 我等结果
- 用户和 Agent 的关系是"委托"

**伙伴的用户期望**：
- 它在持续学习我
- 它记得我说过的话
- 它知道我现在在做什么
- 用户和 Agent 的关系是"陪伴"

在"委托"关系里，用户关心最终结果，不关心过程。"陪伴"关系里，用户感知到 Agent 的"在场感"——它在运转，它在学习，它在准备帮助你。后台任务的可见性是建立这种"在场感"的工程基础。

**设计推论**：M11 的 UI 组件（任务状态 pill）不是辅助功能，不是 debug 工具，是伙伴型产品核心体验的一部分。它应该出现在主 UI 的视觉层级里，而不是藏在 DevPanel 的 log 里。

## 九、实战记录

### 实现历史

**v1（2026-07-25 前）**：内存数组 + fire-and-forget，无状态、无持久化、无通知、无重试、无进度。

```typescript
// v1 实现
backgroundQueue.push({
  name: 'profile-extract',
  fn: async () => maybeExtractProfile(...)
})
```

应用崩溃后任务丢失，用户看不到运行状态，失败无信号，token 混入主会话。

**v2（2026-07-25）**：SQLite 持久化 + 崩溃恢复 + 通知幂等。

核心改动：
- 新增 `background_tasks` 表（id / session_id / type / status / notified / created_at / updated_at / error）
- 状态机：pending → running → completed / failed / cancelled
- `TaskQueueManager` 内部分层：内存队列 + SQLite 持久层
- 启动时从 SQLite 恢复 pending/running 任务（running 重置为 pending）
- `notified` 标志防止重复通知
- 函数重新注册机制：恢复任务通过 type 查找对应实现函数

**v2 已验证**：249 个测试全过（包含 7 个新增持久化测试）。

**v3（2026-07-25）**：在 v2 之上补齐可靠性与可见性——
- 指数退避重试（`MAX_RETRIES=3`，1s/2s/4s，见 `task-queue.ts`）
- UI 任务状态 pill + `profile-extract` 完成/失败 Toast（`App.tsx`）
- `task:event` IPC 订阅

**仍暂缓**：前后台 token 分离（caller 已有、统计未拆）、断线重连、长任务断点续接、后台任务 linked span（可观测交点）。

### 优先级判断（剩余）
