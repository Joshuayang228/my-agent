# 第一部分：认知框架

## 一、第一性原理：调体验需要两间不同的屋子

伙伴产品难调，不只是因为 LLM 黑盒，还因为**人在同一界面上同时扮演三种角色**：

1. **用户**——要被陪伴、被办事  
2. **设计师**——要看色板、控件、空态、错误卡是否「像我们」  
3. **运行时外科医生**——要打开颅骨看 Prompt、记忆、日程、工具调用链现在长什么样  

若三件事挤在一个聊天窗里，结果通常是：主聊天变脏、试验污染真关系、调 UI 没有回归场。

**第一性原理：体验调试 = 透视（现在是什么）+ 试验（改了会怎样）；两间屋子，可以并排入口，不许共用心智。**

```

├─ 推论组 A：三面分工
│     §二 Debug ≠ Playground · §三 对话内调试是叠加 · §四 与 M14 的边界
│
├─ 推论组 B：试验如何不伤真关系
│     §五 会话级覆盖 · §六 先「真」后「全」
│
└─ 推论组 C：体验也是可回归的基础设施

```

> **前置边界**：M14 解决「系统如何留下可查询的痕迹」；本章解决「人用什么界面去读这些痕迹、并安全地做体验试验」。没有 Trace 的 Debug 是空壳；没有 Debug/Playground 的 Trace 只服务工程师终端。

# 推论组 A：三面分工

> 先把屋子分清，再谈里面放什么家具。

## 二、Debug ≠ Playground

| 面 | 回答的问题 | 典型内容 | 失败模式 |
|----|------------|----------|----------|
| **Debug** | 系统*现在*心里有什么？ | Prompt 实装、记忆/日程/事件、LLM 日志、工具与技能状态 | 被做成第二个设置页；或只堆原始 JSON |
| **Playground** | *改了*会怎样？好不好看？ | 会话级 Prompt 覆盖、工具手测、对话试跑、色板/控件/空态/错误卡、aside（蛐蛐）预览 | 直接改生产配置；或只有「单轮 LLM 文本框」却叫 Playground |
| **主对话** | 伙伴感与办事 | 正常 Chat | 默认露出开发者内脏 |

Alice 源码把这拆成两条路由（外加一个开关）：

- `/debug` → **Debug Console**：按「内核 / 生活 / 社交 / 资产 / 用户 / 系统」分组透视世界态与运行时  
- `/playground` → **Playground**：图标、设计系统、UI 控件、对话/模型测试、工具、Skills、MCP、权限、错误卡、提示词编辑器、蛐蛐……  
- `enableDebugMode`（+ `debugActivated`）→ 解锁入口，并允许对话表面叠加调试信息  

**判据**：一个面板若既要「看真相」又要「改了试跑」，默认标签必须说清当前处于哪一面；否则用户不知道自己有没有在污染真会话。

## 三、对话内调试是「透视叠加」，不是第二套产品

主对话默认应是伙伴产品。调试态打开时，允许叠加：

- token / 上下文占用  
- 工具调用展开（若产品策略需要）  
- 开发者入口可见性  

**不允许**的是：关掉调试态后，聊天还残留实验室布局；或未解锁就对普通用户露出 Debug Console。

Alice 用 `enableDebugMode && debugActivated` 这类组合门控——我们认同「双重确认」的方向：设置里开能力 ≠ 当前会话一定处于调试叠加。

**判据**：截一张「调试关」的聊天图，应仍能当产品宣传图用；「调试开」才允许工程师信息密度上升。

## 四、与 M14 的边界：记录 vs 界面

| | M14 可观测性 | M32 体验调试 |
|--|-------------|-------------|
| 产物 | Span / 日志 / 指标 | 人可读的面板与试验场 |
| 消费者 | 代码、Eval、排障脚本 | 产品作者本人（调 Pack、调 UI、调 Prompt） |
| 成功标准 | 事后能解释一次 runaway | 当天能安全改一句 Prompt / 一个色 token 并看见结果 |

Debug 面板应**消费** M14 的痕迹（调用链、事件），而不是另造一套不可对账的「感觉日志」。

# 推论组 B：试验如何不伤真关系

> 伙伴产品的状态是有记忆、有日程、有 MUTABLE 的。试验场必须默认隔离。

## 五、会话级覆盖优先于改生产配置

Playground 里改 Prompt、试工具、预览 aside：**默认只活在当前试验会话**。

生产路径（真会话、真 Pack、真记忆写入）保持干净，除非用户显式「应用到角色 / 写入设置」——且那一步应有确认。

Alice 提示词编辑器文案写得很直白：*修改仅在当前 PlayGround 会话内有效*。我们应把这当成纪律，而不是 UI 文案装饰。

**弯路预警**：DevPanel 若提供「一键覆盖 systemPrompt 全局设置」，会在调语气时毁掉用户已养成的关系；宁可多点一次确认。

## 六、先「真」后「全」

Alice Playground 有二十多个 tab，Debug Console 又有一整棵生活世界树。我们若按清单抄全量，会先得到一个维护不动的博物馆。

**优先序（对我们）**：

1. **真**——工具手测（真实走权限/沙箱）、Prompt 分层实装查看 + 会话级覆盖、关键世界态/记忆透视、调用链（已有 traces）  
2. **稳**——错误卡 / 空态 / 权限确认的可点击样例（体验回归）  
3. **全**——完整 Storybook、Webhook 订阅实验室、狼人杀等产品专属 tab  

**判据**：一个新 tab 若两周内没人用来改产品决策，它就是噪音。

# 推论组 C：体验也是可回归的基础设施

## 七、Token 与组件场不是「设计师玩具」

没有色板页与控件矩阵，前端调性只能靠感觉和截图口嗨——换主题、改 radius、禁左侧 accent 竖线（我们已在视觉语言合同里钉过）无法回归。

Playground 的设计系统 / UI 控件 tab，本质是**体验的单元测试夹具**：人眼当 runner。

这与 `frontend-guidelines` 七公理同一战场；M32 负责「在产品内给它们一个家」，不负责重写设计规范。

## 八、我们优先补什么（产品作者视角）

站在「下周要调 Pack 与 Chat 气质」而不是「做一个 Alice 克隆」：

| 优先级 | 能力 | 为什么 |
|--------|------|--------|
| P0 | 工具手测 | 没有它，权限/沙箱/报错只能赌真对话 |
| P0 | Prompt 实装分层 + 会话覆盖 | 调人设必须看见 L1–L4，且不污染真会话 |
| P1 | 世界态/记忆/日程关键透视 | 伙伴产品的 Bug 经常是「它以为自己在哪」 |
| P1 | 错误卡 / 空态夹具 | 体验回归；比再加一个 JSON 查看器更值钱 |
| P2 | 完整组件 Storybook / Webhook 实验室 | 组件多了再上；外部集成稳定后再上 |

我们现有 DevPanel（Prompt / 薄 Playground 单轮 / 工具注册表 / 系统 / traces / events）已经踩在 M14 上，但**心智仍是「一个侧栏里的杂项」**——下一阶段工程应显式拆成 Debug 面与 Playground 面（可以仍是一个壳，两个主键）。

# 第二部分：实战记录

## 学了什么（Alice 源码，非截图）

| 面 | 落点（本地） | 要点 |
|----|--------------|------|
| Playground | `_extract/page-playground-*.js`，路由 `/playground` | tab 含 icons / design-system / components / chat / tools / prompts / ququ… |
| Debug Console | `_extract/index-*.js` 内 `ZM()`，路由 `/debug` | 分组：内核·生活·社交·资产·用户·系统 |
| 调试开关 | 同主壳 store：`enableDebugMode` / `debugActivated` / `developerModeUnlocked` | 侧栏 Debug 入口与对话叠加信息门控 |
| 主进程 | `alice-source/main-chunks`、`main-index.js` | 早先已解；负责数据面，不负责上述 UI 壳 |

分析笔记 `_reference/alice-debug-mode-analysis.md` 仍有用，但把 Debug 与 Playground 揉成「一个仪表盘」——源码事实是**两路由 + 一开关**。

## 我们有什么

| 项 | 落点 | 对应推论 |
|----|------|----------|
| DevPanel 侧栏 | `src/components/DevPanel.tsx` | 薄观测 + 单轮 LLM 试跑 |
| debug IPC | `electronAPI.debug.*` | 消费 Prompt / tools / system / traces |
| Playground 单轮 | `debug.playgroundRun` | §五 的极简版：免伴侣上下文，尚无会话级 Pack 覆盖 |
| 视觉 token | CSS 变量 + frontend-guidelines | §七 的规范侧已有；缺产品内色板场 |

## 弯路与取舍

1. **只读分析文档就开写**——会把 Debug/Playground 说成同一个东西；必须以 renderer 路由为准。  
2. **想在主聊天里「顺便」做完所有调试**——违背 §三，伙伴感先死。  
3. **按 Alice 二十个 tab 开工**——违背 §六；先 P0。  
4. **本轮只沉淀认知、不改代码**——避免方法论与半成品工程缠车；实施另开施工合同。

## 设计检查清单

1. 用户能否一眼分辨「我在透视」还是「我在试验」？  
2. Playground 的修改默认是否不写进真会话 / 真 Pack？  
3. 调试关掉后，主聊天是否仍像产品而不是 IDE？  
4. Debug 展示的 Prompt/记忆是否与 M14 / 主路径可对账？  
5. 新加的 tab 是否在 P0–P1，还是博物馆展品？
