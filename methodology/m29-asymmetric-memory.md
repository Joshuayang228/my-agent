# 第一部分：认知框架

## 一、第一性原理：能力上可以不对称，治理上必须可透明、可纠错

关系里的记忆天然不对称——她可以记得你忘了的细节。这可以是惊喜，也可以是监视感。  
分界线不在「记没记」，而在：**用户能否看见、纠正、删除；以及她是否在装懂。**

两个伤信任的方向：

1. **多知道却不可治理**——阴档、不可删、用于施压  
2. **其实不知道却装懂**——编造「你上次说…」——比忘记更糟  

```
第一性原理：记忆体验 = 不对称能力 + 对称治理；惊喜止于失信线

├─ 推论组 A：两种不对称
│     §二 多知道 · §三 其实不知道 · §四 为何面板重于口头自称
│
├─ 推论组 B：对称治理
│     §五 可见/可改/可忘 · §六 错记被用上时 · §七 双写与幽灵记忆
│
└─ 推论组 C：边界
      §八 惊喜 vs 失信 · §九 与 MUTABLE/生活/向量的分工 · §十 跨角色
```

> **前置边界**：存储、embedding、去重属 M08。本章是体验契约与治理面，不重写向量算法。

# 推论组 A：两种不对称

> 先承认不对称存在，再决定哪些「用」合法。

## 二、多知道：召回是能力，不是默认炫耀

L3 注入画像 + 向量召回，为的是少问废话、接得住上下文。

| 态度 | 含义 |
|------|------|
| 允许 | 安静用对（「还是短一点」） |
| 鼓励 | 敏感点点明来源并求证（规范层，未强制） |
| 禁止 | 用用户不知存在的档案做操控感发言 |

**判据**：若用户永远无法在产品里发现「她怎么知道的」，多知道就滑向阴档。

## 三、其实不知道：禁止装懂

来源缺口很常见：压缩摘要、召回 miss、换角语境、从未入库。  
行为底线：**不确定就问或承认模糊**，不发明「你说过」。  

与 M27 推回、M21 不编造、M30 叙事不掺假——同一诚实家族。

## 四、为何面板重于口头自称

模型可能说「我记得」，也可能不说。  
**可验证的透明**来自 MemoryPanel（及工具 forget），不是来自旁白表演。  
引用芯片（M29-G1）已落地轻量版：本轮向量 hit → `memory_citations` → Chat 摘要芯片；面板仍是治理真相清单。

# 推论组 B：对称治理

> 用户侧权力：看见、改正、删除——与「她能记」对称。

## 五、可见、可编辑、可遗忘

| 能力 | 入口 | 备注 |
|------|------|------|
| 看见 | MemoryPanel 分类列表 | 地板 |
| 增改删 | Panel IPC；`remember` / `forget` | 模型与用户两条路 |
| 条目纠错 | update / delete | 非整库时间旅行 |
| 人格默契回滚 | Settings MUTABLE 版本 | **另一条栈**（M22） |

**判据**：只有道歉、库里的错行还在 → 假透明。

## 六、错记被用上时的体验路径

理想：

```text
用户：我没说过 / 记错了
  → 模型 forget 或改正（或用户打开面板删）
  → 双写清理
  → 下一轮不再命中
```

现状缺口：

- ~~无本轮 hit 芯片~~ → **M29-G1** 已有摘要芯片  
- ~~无一键纠错~~ → **M29-G2** 芯片「记错了/改正」走双写清理  

产品叙事仍应教用户：**面板是真相清单**；口头「对不起」不够。

## 七、双写与幽灵记忆

结构化库与向量库必须联动删。  
只删 SQLite、向量还在 → 下一轮「阴魂召回」——这是工程失信，不是模型调皮。

写入侧：不索引 assistant 原文（M08 自我强化陷阱）；价值走 profile 提炼。

# 推论组 C：边界

> 什么叫惊喜，什么叫越界；什么不该进记忆库。

## 八、惊喜 vs 失信

| 惊喜（可取） | 失信（禁止） |
|-------------|-------------|
| 接住上周提过的偏好 | 捏造未存储记忆 |
| 面板可核对、可删 | 暗记不可发现 |
| 敏感推断先确认 | 用推断施压 |
| 安静用对 | 炫耀「我知道你的秘密」 |

**30 秒测试**：把 MemoryPanel 给用户看半分钟——是「哦原来记了这些」还是「吓一跳 / 找不到刚才那条」？后者分别指向采集克制（M28）与引用透明（G1）。

## 九、与 MUTABLE / 生活 / 向量的分工

| 存储 | 记什么 | 治理面 |
|------|--------|--------|
| 记忆库 | 用户事实/偏好/feedback | MemoryPanel |
| MUTABLE | 行为默契 | Settings 版本回滚 |
| Moments/Events | 她的日子 | 朋友圈；非用户隐私库 |
| 对话向量索引 | 语义召回原料（用户侧） | 偏内部；勿当第二档案 UI |

**职责错位事故**：把「回复短一点」只写进记忆事实、从不进 MUTABLE → 永远像提醒而不是性格；或把用户隐私写进朋友圈文案。

## 十、跨角色

- 用户画像：**可以**跨主角共享（「用户是谁」）  
- 角色默契与生活：**按 role 分桶**  
- 禁止：小林会话用小周 MUTABLE 假装「我们的默契」  
- ~~反思读 feedback 未按 role 滤~~ → 已收 M22-G2（`listFeedbackForRole`）

# 第二部分：实战记录

## 做了什么

| 项 | 落点 |
|----|------|
| CRUD + 分类 | memory-store · MemoryPanel · IPC |
| 工具三件套 | remember / recall / forget |
| 注入 | buildUserProfile + safeVectorSearch |
| 防自我强化 | 不索引 assistant 原文 |
| 语义去重 | 写入路径（M08 G6） |

## 弯路与取舍

1. **先面板、后引用芯片**——没有可见库，口头透明是空话；芯片是锦上添花但现在仍痛。  
2. **forget 双清**——修幽灵召回比加文案重要。  
3. **记忆与 MUTABLE 分栈**——避免一个「撤销」按钮语义混乱。  
4. **初稿偏短**——补上 30 秒测试、双写失信与跨角色表。

## 设计检查清单

1. 用户能否看到并删除相关条目？  
2. forget 后向量是否还命中？  
3. 是否出现编造「你说过」？  
4. 默契是否误进 MemoryPanel？  
5. 敏感采集是否在冷启动被克制？  
6. 跨角色是否串 MUTABLE？
