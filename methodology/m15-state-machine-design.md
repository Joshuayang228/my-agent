# 第一部分：认知框架

## 一、第一性原理：状态是可命名、可转移、可解释的契约

受 Alice「状态优先」启发（注明：启发自哲学，非照搬实现）：Agent 产品「不靠谱」时，根因多半不是模型笨，而是状态丢了、不同步、或转移说不清。

我们的第一性原理：

**状态不是散落的布尔值和计数器，而是一份契约——有名字、有合法转移、有转移理由、有明确的存活边界（内存还是落盘）。先想清「住哪、谁写、何时转移、为何转移、崩溃后还在不在」，再写功能。**

一旦接受这条，后面都变成推论：何时显式、如何可观测、哪些持久化、系统里已有哪些状态机、Eval 怎么验。

# 推论组 A：选型与归属

> 第一性原理说「有名字、有合法转移」。现实里不是每个计数器都值得画状态图——选型错了要么过设计，要么意大利面。

## 二、显式 FSM vs 隐式状态：选型判据

| 倾向 | 形态 | 何时选 |
|------|------|--------|
| **显式 FSM** | 命名状态联合类型 + 集中转移（或转移表）+ 非法转移拒绝 | 多恢复路径、跨重启、要对用户可见、要被 Eval 断言 |
| **隐式状态** | `LoopState` 字段 + `while` + `ContinueReason` 跳转信号 | 单次调用生命周期内、状态随函数结束销毁 |
| **不要状态机** | 纯函数 / 一次计算结果 | 无跨步记忆、无「当前处于哪一相」 |

我们的实际选择（不是教条）：

| 子系统 | 形态 | 为什么 |
|--------|------|--------|
| Agent Loop | **隐式**（`LoopState` + `while` + `ContinueReason`） | 一次 `agentLoop()` 跑完即扔；需要回退 turnCount，所以用 while 而不是 for（→ M01） |
| 后台任务 | **显式五态** `TaskStatus` | 用户可见 pill、跨崩溃恢复、通知幂等（→ M09） |
| 执行模式 | **显式三态** `ExecutionMode` | 用户可配信任等级；可在运行中只降不升（→ M10） |
| MCP 连接 | **显式四态** | 设置页要显示绿/黄/红点；连接失败要有 error |
| UI 流式中 | **隐式**（`streamingSessionRef` 等） | 渲染层观感状态；权威仍在主进程事件流 |

**判据一句话**：若「当前处于哪一相」会影响用户可见行为、跨进程恢复、或测试断言——就该有**命名类型**；若只在一次函数调用里活着——集中到一个 state 对象即可，不必上状态机框架。

反面教材：用一堆互不相关的 `let isXxx` 散落在文件各处，没有人能画出合法转移图——这就是「有状态、无契约」。

## 三、系统里的状态机图鉴（索引）

> 细节在各章；这里只保证「新人能找到所有叫状态的东西」。

```
┌─ 运行时（单次交互）──────────────────────────────┐
│  LoopState + ContinueReason + TerminalReason      │ → M01
│  ExecutionMode（可被 Denial Tracking 降级）       │ → M10
│  Span.status: running → ok|error                  │ → M14
└───────────────────────────────────────────────────┘

┌─ 跨交互 / 跨重启 ────────────────────────────────┐
│  TaskStatus 五态 + notified                       │ → M09
│  会话消息 / settings / memories（SQLite）          │ → M08 / storage
│  MCP: connecting|connected|error|disconnected     │ → M13
└───────────────────────────────────────────────────┘

┌─ 产品层（计划 / UI）─────────────────────────────┐
│  task-plan: pending|in_progress|done|skipped      │ → 工具 task_plan
│  UI streaming / tool card 本地态                  │ → renderer（非权威）
└───────────────────────────────────────────────────┘
```

**权威原则**：渲染进程的本地态只能是**投影**，不能是真相源。会话读写若仍由 UI 承担，会和主进程抢权威——这是 wishlist「会话 Runtime 中心化」要解的问题，不是本章实现范围。

# 推论组 B：可观测与恢复

> 第一性原理说「可解释」和「存活边界」。没有 reason 的转移无法调试；错放持久化要么丢恢复，要么把瞬时计数写成库污染真相。

## 四、转移必带 reason

Alice 可观测性哲学与我们 M14 合流到一条纪律：

**凡是「改变系统相」的转移，对外或对日志必须留下 reason（或等价结构化字段）。**

| 转移 | 我们的 reason 形态 | 谁消费 |
|------|-------------------|--------|
| Loop 结束 | `done.reason: TerminalReason` | Runtime 善后、UI、Eval grader |
| Loop 非标准跳转 | `ContinueReason`（内部） | 仅 loop 控制流；不进事件流 |
| 执行模式降级 | `execution_mode_changed.reason` | 前端提示 + 设置持久化 |
| 任务失败 | `BackgroundTaskInfo.error` + 事件 | UI pill / Toast |
| 权限拒绝 | `deniedTools[].reason` + tool_result | 下一轮 prompt / Deny-and-Continue |
| MCP 失败 | `connection.error` | 设置页 |

`ContinueReason` 可以只活在 loop 内部——因为它解释的是**控制流跳转**，不是用户可见终态。但 `TerminalReason` **必须**出事件：空的 `{ type: 'done' }` 让 Runtime 无法区分「正常结束该抽记忆」和「熔断了别瞎忙」。

判据：**若半年后你只能靠猜「为什么从 A 到了 B」，这条转移就欠一个 reason 字段。**

## 五、持久化边界：内存 vs SQLite

| 必须落盘（跨重启要一致） | 可以只活内存（单次 Loop / 进程内） |
|--------------------------|-------------------------------------|
| 会话消息、标题 | `turnCount`、`consecutiveDenials` |
| `ExecutionMode` / 沙箱 / permissionRules 设置 | `hasAttemptedReactiveCompact` |
| `TaskStatus` + `notified` + `retryCount` | `ContinueReason` / 当前 transition |
| 记忆条目 | Span 树（可另做采样落盘，见 M14） |
| MCP 服务器**配置**（不是瞬时 connecting） | MCP 瞬时 `connecting` 相 |

三条红线：

1. **用户可见且承诺跨会话的 → 落盘。** 后台任务 pill 在崩溃后若「假装从没发生」会伤伙伴信任（→ M09）。
2. **单次对话内的熔断计数 → 不落盘。** 把 `consecutiveDenials` 写成库，重启后带着旧惩罚继续，语义错误。
3. **执行函数（`fn`）不能序列化。** 任务恢复只能恢复**元数据**，函数要重新注册——持久化的是契约状态，不是闭包。

# 推论组 C：交点与纪律

## 六、与相邻模块 / Eval 的交点

| 模块 | 交点 |
|------|------|
| M01 Loop | 隐式状态机的样板：`LoopState` 集中 + `TerminalReason` 出门 |
| M09 任务 | 显式五态 + 落盘 + 幂等通知的样板 |
| M10 权限 | `ExecutionMode` 转移「只降不升」；子 Agent 继承同纪律 |
| M14 可观测 | reason / Span 是「转移可解释」的基础设施 |
| M16 并发 | 状态机若并发写，需要锁或串行队列（任务队列已串行） |
| M17 / M18 | Eval 大量场景断言 `TerminalReason` / `execution_mode_changed`——**状态契约即测试契约** |
| M12 IPC | 事件把状态投影到渲染进程；四处同步防止「类型有、桥没有」 |

**对 Eval 的含义**：新终止原因、新任务态、新执行模式，必须同步 grader 与场景——改状态枚举却不改断言，等于默许静默漂移。

## 七、刻意不做

1. **不上通用状态机框架**（XState 等）——现有几台状态机规模小，框架成本高于收益；纪律靠类型 + 检查清单。
2. **不把 UI 本地态提升为权威**——投影可以脏，真相在主进程。
3. **不在本章实现「会话 Runtime 中心化」**——已在 wishlist，属架构债，单独立项。
4. **不强制所有内部 flag 都变成联合类型**——`hasAttemptedReactiveCompact` 这种一次性机会布尔，留在 `LoopState` 即可。
5. **不把 MCP 连接态方法论化成第二套 M13**——图鉴收录；协议细节归 M13。

## 沉淀：状态机设计检查清单

1. 这个功能涉及哪些**命名状态**？能画一张转移图吗？
2. 状态活在**内存还是 SQLite**？崩溃后用户是否会感知不一致？
3. 每次对外可见的转移，有没有 **reason / error / code**？
4. 渲染进程拿的是**投影还是权威**？
5. 新枚举值有没有同步 **Eval grader / 场景**？
6. 是该上显式联合类型，还是收进一个 `XxxState` 对象就够？
7. 是否和已有状态机**同名不同义**（如 task-plan vs TaskStatus）？命名能否消歧？
