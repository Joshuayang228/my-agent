# 第一部分：认知框架

## 一、第一性原理：扩展点首先服务运行时，用户扩展另有通道

做「Hook 系统」时最容易犯的错，是看见 Claude Code 有 settings.json 里的 PreToolUse，就默认我们也该有一份。但那是**开发者工具**的扩展面——用户本人往往就是会写 shell 的人。

我们的产品是人格化桌面**伙伴**。终端用户要的是：换人格、记偏好、接 MCP、装 Skill、调审批——不是在 JSON 里配生命周期脚本。若把 CC 式用户 Hook 做成一等功能，产品会被拽向「可编程 Agent IDE」，和差异化（关系 / 人格）抢注意力。

第一性原理：

**扩展点首先服务运行时的正确性与可演进；对伙伴产品，用户可见的扩展走 Skill / MCP / 人格 / 设置，不走生命周期 Hook。**

一旦接受这条，后面所有设计都变成分层问题——**谁在扩展、扩展能不能拦主流程、失败了能不能拖垮对话**：

# 推论组 A：扩展点必须分层

> 第一性原理说「服务运行时」，但运行时里已经堆了 Middleware、事件流、Tracer、权限链。不分层就会把「打点」「改权限」「通知 UI」塞进同一个叫 Hook 的口袋。

## 二、三层模型：观测面 / 控制面 / 通知面

| 层 | 名字（我们用的词） | 能不能否决主流程 | 典型职责 | 参考 |
|----|-------------------|------------------|----------|------|
| **观测面** | Observer / Tracer | **否** | Span、耗时、token、日志 | feiche Observer |
| **控制面** | Policy /（内部）Hook | **能**（显式） | 权限、确认、改工具可见集、拦截执行 | CC Hooks（能力参考，非产品形态） |
| **通知面** | Event 流 | **否**（审批回调是旁路） | UI 渲染、落盘、Toast | 我们的 `AgentStreamEvent` |

三条硬边界：

1. **观测面禁止获得否决权**——metrics 实现 panic 或返回「deny」都不该挡住用户对话。feiche 的 Observer 不返回决策，就是这个纪律。
2. **控制面可以否决，但必须显式、可审计**——不是靠「stderr 打两行字」暗示模型。
3. **通知面默认不参与策略**——`tool_confirm` 等待用户是**控制旁路**，不是「事件消费者变成了 Hook」。

判据：**如果你分不清一个扩展点属于哪一层，先别加；加错层比缺少扩展点更伤架构。**

## 三、四个易混概念：Hook / Event / Middleware / Observer

| 概念 | 我们代码里是什么 | 层 | 常见误用 |
|------|------------------|----|----------|
| **Event** | `AgentStreamEvent` yield → IPC → UI | 通知 | 把「监听事件」当成「可插策略」 |
| **Middleware** | `ToolMiddlewarePipeline` 洋葱模型 | 控制（工具执行期横切） | 以为有了 Middleware 就等于有了用户 Hook |
| **Observer/Tracer** | `startSpan` / 日志 | 观测 | 给 Tracer 加「失败则中止工具」 |
| **Hook（理想）** | **我们刻意不做用户态**；内部若需要，应是显式控制面 API | 控制 | 照搬 CC settings hooks |

当前真实链路（读代码时应按这个顺序想）：

```text
filterTools（可见集，控制）
  → LLM
  → checkToolPermission + confirmTool（控制闸门）
  → ToolMiddleware（执行横切，控制）
  → tool.execute
  → yield AgentStreamEvent（通知）
  → Tracer span（观测，旁路）
```

# 推论组 B：控制面的纪律

> 即便不做用户 Hook，内部控制面（权限、Middleware、filterTools）仍要遵守和 CC 相同的几条纪律——否则「失败拖垮对话」「allow 偷偷越权」一样会发生。

## 四、失败默认可继续，阻断必须显式

受 CC Hooks 启发（注明：启发自协议设计，非照搬产品形态）：

| 信号 | 含义 |
|------|------|
| 观测失败 / 中间件非关键错误 / 日志失败 | **不拖垮**主对话 |
| 权限 deny / 用户拒绝确认 / 熔断 | **显式阻断**，并留下可解释结果（tool_result / 错误码） |

伙伴场景更需要这条：人格脚本、记忆旁路、遥测若走「失败即停」，一次旁路故障就会毁掉陪伴感。

判据：**默认路径是「扩展挂了，对话还在」；只有安全与用户意志才能把默认改成停。**

## 五、扩展输出是结构化协议，不是日志

控制面若要影响 Agent，必须走一等字段，而不是往 stderr 打字指望模型「看懂」：

- 拒绝 → 明确的 tool_result / `AgentErrorCode` / Deny-and-Continue 提示
- 改可见工具集 → `filterTools` 返回新数组
- 改执行参数 →（若未来做内部 hook）`updatedInput` 一类结构，而不是改全局单例碰运气

通知面可以是文案；控制面必须是协议。

## 六、扩展建议不能越过权限引擎

CC 的纪律：PreToolUse 的 `allow` **不能绕过** settings 里的 deny/ask。

落到我们：

- Middleware / 未来任何内部 hook **不得**把 `full-access` 或跳过确认当成「方便调试」的默认捷径
- Skill / MCP 扩大能力时，仍要过沙箱与审批模式
- 「人格代用户做决定」可以**建议**，最终裁定在权限层（M10）

判据：**有性格仍安全 = 人格与扩展可以提议，权限引擎最终说了算。**

# 推论组 C：产品边界与取舍

## 七、什么该做成扩展点，什么该改框架

| 情况 | 做法 |
|------|------|
| 横切、可插拔、失败可隔离（日志、结果落盘、语法校验） | **扩展点**（Middleware / 内部 callback） |
| 改变 Agent 语义或信任边界（权限模型、压缩策略、人格 PROTECTED） | **改框架**，写进对应方法论章 |
| 用户要「多一种能力」 | **Skill / MCP**，不是 lifecycle Hook |
| 用户要「换一种相处方式」 | **人格 / 记忆 / 设置**，不是 Hook |

## 八、用户扩展的正确通道

| 用户意图 | 通道 | 为什么不是 Hook |
|----------|------|-----------------|
| 多会一门手艺 | Skill（Markdown + `allowed_tools`） | 按需激活、可版本回滚（M20） |
| 接外部系统 | MCP | 标准协议、工具动态注册 |
| 换性格 / 关系感 | 人格引擎（M21） | 一致性与成长性，不是脚本 |
| 松/紧审批 | 执行模式 + 沙箱（M10） | 信任等级配置，不是 PreToolUse |
| 长期记得我 | 记忆系统（M08） | 数据面，不是生命周期回调 |

## 九、刻意不做（写进认知地图，避免以后又捡回来）

1. **不做 settings.json 用户 lifecycle Hook**（PreToolUse shell 等）——产品形态不匹配。
2. **不把 Observer 做成可拦截接口**——观测与控制必须拆开（受 feiche 启发）。
3. **不把 AgentStreamEvent 消费者升级成插件市场**——事件是通知面。
4. **不在本轮实现「通用内部 Hook 总线」**——现有 Middleware + Permission + filterTools 已覆盖主路径；真出现第三个内部调用方再抽，避免过设计。
5. **Alice 范式一不进本章**——进 M04。

若未来极客用户强烈要求「后门」，只能作为**隐藏高级能力**单独立项，默认关闭，且仍不得越过权限引擎——不是 M11 的默认交付。

# 第二部分：实战记录

## 学 / 审做了什么（2026-07-26）

三路并行：

1. **CC**：真正的 Hook 引擎在 `utils/hooks.ts`（不是 `src/hooks/` 的 React hooks）；28 类事件；settings/plugin/session 多源；exit 0/2/其他 + JSON 协议；失败默认可继续。
2. **feiche**：Observer 四对 Start/End，纯观测；CompositeObserver 顺序 Start / 逆序 End；与 Callback（推 UI）分离。
3. **我们**：有 Middleware / Event / Permission / filterTools / Tracer；**无**用户可配置 lifecycle Hook；`middlewarePipeline.use` 生产路径零调用方。

产品对齐结论：**用户不需要 CC Hook；我们需要把分层写清楚，并守住「观测不能拦」。**

## 与现有模块的交点

| 模块 | 交点 |
|------|------|
| M01 Loop | 事件流是通知面；权限/确认是控制面嵌入点 |
| M04 工具 | Middleware 是执行期控制横切；声明式契约是元数据，不是 Hook |
| M07 压缩 | G9「压缩前后 hooks」——若做，只能是**内部**观测/控制回调，不做用户配置；当前仍暂缓 |
| M10 权限 | 控制面的最终裁定者；扩展不得越权 |
| M13 MCP | 用户侧能力扩展主通道之一 |
| M14 可观测 | 观测面本体；禁止获得否决权 |
| M20 Skill | 用户侧能力扩展主通道之一 |

## 暂缓 / 另案

| 项 | 归属 | 说明 |
|----|------|------|
| shell 权限未统一走 `checkCommandPermission`、`loadRules` 未接线 | **M10 安全债** | 与「要不要用户 Hook」无关；不在本轮 M11 实现 |
| Middleware 对外注册 API / 文档化插件入口 | 内部演进 | 有第三个真实调用方再做 |
| 压缩前后内部回调（原 G9） | M07 × 内部扩展 | 需求出现再加，默认仍走 Tracer 观测 |
| 通用内部 Hook 总线 | 过设计风险 | 暂缓 |

## 沉淀：扩展点设计检查清单

1. 这个扩展点属于观测 / 控制 / 通知哪一层？能不能一句话说清？
2. 它失败时，用户对话是否仍能继续？
3. 它若能阻断，阻断信号是否结构化、是否可审计？
4. 它能否绕过权限引擎或沙箱？若能——设计错误。
5. 用户想多一种能力时，引导的是 Skill/MCP，还是 lifecycle Hook？后者应拒绝或降级为隐藏高级选项。
6. 是否误把 Alice「声明式契约」当成 Hook 需求？

## 决策记录

| 决策 | 选择 | 理由 |
|------|------|------|
| 用户 lifecycle Hook | **不做** | 伙伴产品用户扩展通道已是 Skill/MCP/人格 |
| 本轮是否写 Hook 运行时 | **不写** | 认知地图优先；避免过设计 |
| 三源怎么用 | CC 学纪律、feiche 学观测边界、Alice 范式一归 M04 | 三者不是同一问题 |
| P0 权限接线 | **不并进本轮** | 安全债单独立项，避免 M11 变杂烩 |
