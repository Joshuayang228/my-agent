# 第一部分：认知框架

## 一、第一性原理：在场是「世界还在过」的可感知证明，不是刷存在感

纯被动问答 = 抽屉里的工具：用时灵，不用时等于死。
但另一极端同样糟糕：定时「想我了吗」——没有日子真相，只有通知配额，用户很快学会右键关闭。

我们要的是第三种：**不聊的时候，活跃主角的日子仍可能推进；用户打开时能看见；触达若发生，必须带着世界增量，而不是情绪绑架。**

# 推论组 A：如何证明她还在（不靠骚扰）

> 第一性原理前半：证明来自世界，不来自话术。

## 二、在场层级：从静到闹

| 层级 | 含义 | 用户成本 | 我们现状 |
|------|------|----------|----------|
| L0 静默推进 | active 角色 ticker 物化事件 | 零（可无感） | ✅ |
| L1 打开可见 | 欢迎屏 / 圈 / 柜有内容 | 主动打开 | ✅ |
| L2 轻提示 | 「有新动态」类气泡 | 低打扰 | ✅ M31-G1（可静音） |
| L3 桌面通知 | 系统级打断 | 高 | △ 仅失焦回复，非生活 |
| L4 定时问候 | 找上门聊天 | 最高 | ✅ M31-G3（默认关） |

**判据**：层级越高，对「内容必须派生自 World 且有信息增量」的要求越严。L0/L1 可以厚做；L3/L4 没想清勿扰模型前不做满。

## 三、打开即在场

空会话不是空白输入框，而是：

- `嗨，我是{名}`
- 一句角色描述
- 提示：圈/柜/聊天跟当前主角；对话中不能换人

这是**成本最低、争议最小**的在场——不抢操作系统焦点，却完成「这里有人」的第一眼。

换角后欢迎跟随新 `activeRoleId`；**不**重置成长时钟（M28）。文案主进程与渲染共用 `buildColdStartCopy`，避免两处文案漂移成两个她。

## 四、截面 > 空聊句

「活人证明」优先顺序：

1. **Moments**——published 事件的可见投影（有日期、有活动）
2. **Assets**——还在的物（连续性）
3. **Catch-up 摘要**——你离开期间她补上的近况（换角/回归）
4. 口头「我想你了」——无 World 依据时价值接近零

**判据**：若关掉所有推送，用户只靠打开 App，是否仍能感到日子在过？若不能，说明在场绑在了通知上，根子虚。

这与 M24「禁止独立朋友圈真相」同一刀：在场内容不得另造。

# 推论组 B：若要触达，怎么触

> 第一性原理后半：触达克制；有增量才配打断。

## 五、时机 · 形式 · 内容

| 维 | 原则 | 反例 |
|----|------|------|
| **时机** | 有新 published moment；长任务完成；用户可能空闲 | 深夜连环推；无增量重复推 |
| **形式** | 应用内截面 > 应用内轻提示 > 桌面通知 > 系统推送 | 一上来就系统推送段子 |
| **内容** | 派生 World 或真实任务状态；一句话能说清增量 | 「嗨～」无信息；编造假行程 |

**已实现（M31-G2）**：默认本地 22–8 勿扰 + 每日最多 3 条；可在设置调整。规范上默认偏保守——宁可少推，不可冤推。

## 六、通道分工

| 通道 | 职责 | 不是 |
|------|------|------|
| 欢迎屏 | 身份在场 | 生活流水账全文 |
| Moments / Assets | 生活在场 | 聊天替代品 |
| Cast / 忙闲 presence | 召唤前「她现在方便吗」 | 主线推送 |
| 桌面 Notification（现） | 失焦时**回复可达** | 生活动态主通道 |
| 任务 pill / 后台任务完成 | 干活进度 | 情感刷屏 |
| 定时主动问候 | 默认关；近 Moment 派生的找上门气泡 | DAU 黑客 / 空喊想念 |

## 七、查询式在场 vs 推送式在场

| | 查询式 | 推送式 |
|--|--------|--------|
| 谁发起 | 用户（开聊/看圈/召唤前检查） | 系统 |
| 例子 | `describeCastPresence`；打开 MomentsPanel | 「你有一条新动态」 |
| 风险 | 低 | 打扰、依赖 |

当前仍以**查询式** + **静默 L0 推进**为主，但已开放两个窄而受控的主动口：新 Moment 应用内轻提示，以及默认关闭、每日一次的主动问候。两者都受静音、冷却、勿扰、日预算和 Presence 门闸；窗口失焦回复通知仍属于干活线可达性。

**判据**：新增任何推送前问——没有这条推送，世界真相是否仍在？若否，先修世界；若是，再谈要不要吵用户。

# 推论组 C：伦理与产品指标

> 在场可以温暖，但不能变成绑架或噪音。

## 八、打扰感与依赖感

- **打扰**：高频、无增量、打断心流（写代码时弹「想吃糖吗」）
- **依赖**：设计成「不回她就愧疚/她会消失」——情绪勒索，我们明确不做

桌面 Agent 尤其危险：用户把我们当同事级工具，容忍度低于纯陪伴 App。
**默认策略**：先做厚 L0/L1，再谨慎加 L2；L4 需要单独产品评审。

## 九、「想打开」而不只是「需要时才打开」

成功体感（定性）：

- 愿意点开朋友圈看一眼今天怎样
- 空会话不觉得冷
- 真要干活时，她在且不挡事

失败体感：

- 通知栏一排「想我了吗」被关掉
- 打开只有输入框，圈是空的（或假的）
- ticker 卡死主进程 / 抢焦点

**不是**通知 CTR、不是打开次数最大化。伙伴产品的在场 KPI 更接近「还想维持这段关系」，而不是「还想点广告」。

## 十、与干活、叙事的边界

| 冲突 | 优先级 |
|------|--------|
| 生活提示 vs 工具确认弹窗 | 干活确认优先；生活提示让路 |
| 在场话术 vs 同源日子 | 叙事诚实优先（M30）；宁可少说 |
| 召唤 presence vs 推进对方生活 | 只查询，不 tick（M26） |

主动在场**加强**「她是同一个人」，不得用假日子制造虚假连续（M30 §四）。

## 弯路与取舍

1. **差点先做定时问候**——没有稳定 Moments 时，问候只能瞎编；先 W3 投影再谈 W6 触达，顺序正确。
2. **欢迎文案曾主进程/渲染各写一份**——漂移成两个开场白；抽到 shared 是小修复、大体验。
3. **桌面通知复用回复通道**——避免再开一套「生活推送」权限与文案，降低打扰面。
4. **初稿方法论偏目录**——补上在场层级、查询/推送分界与伦理，避免「在场=多推送」误读。

## 设计检查清单

1. 空会话是否一眼有人？文案是否跟当前 active？
2. 无对话一段时间后，active 的 Moments 是否可能增加？（L0）
3. 任何推送是否带得出来 World/任务增量？
4. 非活跃角色有没有在后台刷圈？（应没有）
5. ticker 失败会不会拖垮 Loop？
6. 有没有用愧疚话术驱动打开率？
