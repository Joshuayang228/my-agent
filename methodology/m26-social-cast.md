# 第一部分：认知框架

## 一、第一性原理：卡司是「活跃主角视角下的圈子」，不是聊天室里的并列主角团

同宇宙可以有多个可切换主角，但**每一刻对话只有一个「我」**。其他人应以「你认识的人」出现：短关系、可召唤，而不是把三份 PROTECTED 糊进同一 system prompt 演群戏。

最容易踩的坑：

1. **名册灌全文**——把小林/小周的 protected 都塞进 Prompt → 身份串味、token 爆炸。  
2. **召唤 = 换活跃**——点开聊朋友却改了 `activeRoleId`、推进了对方生活 → 世界状态被串门毁掉。  
3. **卡司 = Swarm**——把人设包装和 M19 多 Agent 编排混为一谈。

第一性原理：

```
卡司 = 以 active 为视角的关系网 + 可浅注入 + 可召唤装载；不偷换「我」，不私推别人日子

├─ 推论组 A：在主对话里怎么出现
│     §二 relations 是边 · §三 名册只许短句
│
├─ 推论组 B：召唤与忙闲
│     §四 子会话装载完整 Pack · §五 可用性软拦
│
└─ 推论组 C：边界
      §六 多主角槽 ≠ 同屏群聊 · §七 卡司 ≠ M19 编排
```

# 推论组 A：在主对话里怎么出现

## 二、relations 是宇宙资产上的边

`relations.json`：`from` / `to` / `type` / `note`。  
组装时以 `activeRoleId` 为视角，把边转成「你与 X（同事）：…」。  
NPC 可以不在 `protagonistIds`（如 chen/ayu）；主角之间也可以有边。

**禁止**在每个角色的 protected 里各写一套互相矛盾的小传——关系真相在边与 summary，不在三份圣经互抄。

## 三、名册浅注入：summary / note，绝不他人 protected

Prompt 块声明：「这是名册摘要，不是他们的完整人设；不要假装成为他们。」  

判据：主对话 system 里出现其他角色的全文 PROTECTED → 架构违规（Eval C01 盯这个）。

# 推论组 B：召唤与忙闲

## 四、召唤 = 子会话装载，不改世界主权

| 做 | 不做 |
|----|------|
| `session_kind=summon` 新会话 | 改 `activeRoleId` |
| 装载对方完整 Pack（含 protected） | tick / Catch-up 对方生活 |
| CastPanel「开聊」 | 自动反思写对方 MUTABLE |

用户要的是「跟这个人聊一会儿」；生活世界的主权仍在当前活跃主角。聊完回去，世界时间线不乱。

## 五、可用性：可婉拒，可 force

对照 Alice `checkFriendAvailability`：忙时段 / 忙日 / 随机婉拒 + 改约建议；日程槽位优先于静态表。  
`force` 仍可强开——产品给用户最终决定权，忙闲是角色感不是硬墙。  
查询纯只读，不 resume 对方。

# 推论组 C：边界

## 六、三主角槽是「可切换的我」，不是「同时三个我」

架构挂满 `protagonistIds`（小林/小周/小夏）≠ 主对话三角色同台。  
切换 = 完整换「我」+ pause/catch-up（M23）；召唤 = 临时以对方身份聊（不换主权）。

## 七、卡司人设包装 ≠ M19 多 Agent 编排

| | 卡司（M26） | 多 Agent（M19） |
|--|------------|----------------|
| 目的 | 关系感、风格一致的「谁」 | 任务拆分、并行工具 |
| 入口 | relations / summon / roster | subagent / 编排器 |
| 失败模式 | 身份串味、偷推进生活 | 权限泄漏、结果合并乱 |

可以未来让「朋友」以子 Agent 身份帮干活，但必须先守住人设与生活边界——先 M26，再接到 M19。

## 弯路与取舍

1. **先浅注入再召唤装载**：主对话安全第一。  
2. **召唤带完整 Pack**：串门要像那个人，但不能动其生活引擎。  
3. **忙闲可 force**：角色感服务体验，不绑架用户。
