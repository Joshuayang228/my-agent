# 第一部分：认知框架

用户感到「她有在过日子」，最直觉的截面是朋友圈式时间线。  
最容易翻车的做法：运营/模型**直接写朋友圈文案**，事件库却是空的——对话里在咖啡馆，圈里在海边，世界碎了。

# 推论组 A：两层职责与寿命

> 第一性原理落到存储：谁是真相，谁只是缓存。

## 二、事件层是真相；Moments 是派生缓存

| 层 | 存什么 | 可否独立编造 |
|----|--------|--------------|
| **Event** | type / scheduledAt / status / payload | **否**——剧本物化或引擎写入 |
| **Moment** | text + meta + **eventId** | **否**——必须从 published 事件投影 |

**判据（重建测试）**：删掉 `companion_moments` 整表，只要 events 还在，应能**幂等**跑投影重建时间线。若不能，说明 Moments 偷存了独立真相——架构违规。

## 三、动态可沉，事件仍在

产品时间线可只展示近期；旧 Moment 行可不查询甚至清理。  
**事件**仍留在生活史上（至少细补窗与审计需要范围内），供 Catch-up、调试、未来聊圈一致性。  

**判据**：「圈沉了」≠「那天没过」。用户刷不到旧帖，不等于世界删除那天。

## 四、文案朴素优先于华丽

当前文案是规则拼接（活动 + 心情 + 地点 + 可选着装），不是 LLM 小作文、不是生图。  

| 阶段 | 目标 |
|------|------|
| 现在 | 可见、同源、可测 |
| 以后 | LLM 润色仍**绑定 event**（M24-G2）；生图非本阶段（M24-G3） |

**弯路预警**：先上华丽文案再补事件，必然双真相。顺序必须是事件 → 投影 →（可选）润色。

# 推论组 B：何时发生、给谁看

> 第一性原理落到时间与权限：未发生的不上圈；别人的圈不混刷。

## 五、状态机：planned → published → project

```text
DayScript 槽位 → insertEvent(planned)
tick / Catch-up → scheduled_at 落入窗 → markEventPublished
               → projectMomentFromEvent（幂等）
```

| 状态 | 含义 |
|------|------|
| planned | 排了，还没「发生到该时刻」 |
| published | 对世界已发生 |
| moment | 用户可见的一条动态 |

**禁止**：跳过事件 `insertMoment`；给 unpublished 发朋友圈。

## 六、仅 activeRoleId 的时间线对用户可见

存储按 `roleId` 分桶；IPC/UI **再限**当前 active。  
切换主角 = 换一整面生活 UI，三人动态不混刷。  
非活跃：不 tick → 不偷偷刷圈（M23 暂停哲学）。

**判据**：设置里是小林时，MomentsPanel 是否可能冒出小周的帖？冒出即事故。

## 七、Catch-up 细窗只物化「该角色」

完整切换回来时：细补 ≤7×24h 内该角色的 planned→published→moment。  
不是把宇宙里所有人的动态追平。  
概况摘要（更早空洞）进角色状态/Prompt，**不**假装逐日发帖。

# 推论组 C：和对话、资产、在场的边界

> 截面服务感知，不抢干活，不拥有物真相。

## 八、与对话一致性：薄约束，先同源

理想：聊天提到的地点/情绪与最近 Moment 不打脸。  
现状：

- Prompt 吃 Catch-up + **近 1–3 条 Moment 薄锚点**（M24-G1），**不**整库灌圈  
- 软校验 `checkReplyAgainstRecentMoments`（地点打脸启发式）；**不**阻断 Agent Loop  

**立场**：宁可圈朴素、对话偶尔略不同步，也不要两套文案各写各的。同源是地板；硬拦回复是天花板。

## 九、可挂衣柜，不拥有资产

moment 槽可带 `assetId`；投影时读资产名拼进 text/meta。  
着装真相在 Assets（M25）；圈只**引用**。  
资产删了：动态降级为无着装句，事件仍在——不反向用圈文案当衣柜。

## 十、在场用截面，不另造生活

M31 的 L1 在场优先看 Moments/Assets。  
若推送/问候的内容不能回溯到 event，就是假在场（与 M30/M31 一致）。

# 第二部分：实战记录

## 弯路与取舍

1. **投影缓存 vs 每次 join**：列表快；重建函数保留——缓存不是真相。  
2. **纯文本**：躲开生图范围爆炸，先验证同源闭环。  
3. **一致性校验后置**：没有稳定事件时做裁判只会误伤。  
4. **初稿偏短**：补重建测试、Catch-up 范围与在场接缝。

## 设计检查清单

1. 删 moments 表后能否从 events 重建？  
2. 有无无 eventId 的孤儿动态？  
3. planned 是否提前上圈？  
4. 非 active 是否出现在 UI？  
5. 是否存在不经事件的写圈入口？  
6. 着装是否只来自 assetId 解析？
